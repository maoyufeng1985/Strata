# q36：上腿 fp16（2026-10-23）

配套：[2026-10-21-q36-peer-ima-root-cause.md](2026-10-21-q36-peer-ima-root-cause.md) §13.7–13.8、
[2026-10-23-q36-ev-wait-optimization.md](2026-10-23-q36-ev-wait-optimization.md)。

状态：**设计定稿，待实施**。基线 = 并行 prepare 之后（`bin/strata-q36.parallel-prep` = `7f1ae9f6`），
warm bench 1/2 = **310.2 / 311.4 tok/s**，41.03 ms/层。

## 0. 为什么是上腿

实测基线的每层时间去向（全部 ms/层，探针 `STRATA_Q36_PROMPT_TIMING=1`）：

| 段 | ms/层 | 能不能动 |
|---|---|---|
| **helper_wait** | **16.43** | 上腿 30 MiB/层：D2H 过 helper 的 Gen1 x4（并行）+ H2D 过主卡 Gen3 x8（**串行**）→ **带宽墙，只能减字节** |
| plan | 8.50 | D2H staging 仍串行（2.79 ms/层）→ 合并成一次可省 ~1.9 ms/层（候选 D） |
| primary_work | 8.14 | 主卡自己的活（共享专家） |
| mixer | 7.09 | GDN / attention |

**上腿的字节**：每个 helper 回传 `n = 1365` 行 × `n_embd = 2048` 个 fp32 = **10 MiB**；
3 个 helper = **30 MiB/层**，两个方向各 30 MiB。

- D2H（helper → host）：三条**独立**的 Gen1 x4，**已经并行** → 30 MiB / 3 = 每条 10 MiB @ 1.25 GB/s ≈ **8.7 ms**
- H2D（host → 主卡）：三条在**主卡的同一条 stream** 上 → **串行** → 30 MiB @ Gen3 x8 ≈ **3.9 ms**

**fp16 后各减半**：D2H 8.7 → 4.4 ms，H2D 3.9 → 2.0 ms。
`helper_wait` 里上腿占大头 → 预计省 **~5 ms/层** → 41.03 → ~36 ms/层 → **~355 tok/s（+14%）**。

## 1. 改什么

**旗标**：`STRATA_Q36_PEER_F16=1`（精确 `"1"`，函数局部静态，与 `helper_timing()` 同写法）。
**默认关 → 默认路径逐字节不变**（AGENTS.md 的硬要求）。

### helper 侧（`src/qwen35/q36_peer_prefill.cu` + `.cuh`）

| 改动 | 内容 |
|---|---|
| `m.d_out16` | device `__half` 缓冲（`nf * n_embd`），打包的落点 |
| `m.h_out16` | pinned `__half` 缓冲（`nf * n_embd`），D2H 的落点 |
| `k_pack_f16` | 打包核：`src`（fp32）→ `dst`（fp16），`n` 个元素 |
| `launch()` | fp16 模式下：`k_pack_f16<<<>>>(m.d_out, m.d_out16, n*n_embd, m.stream)` → D2H 传 `n*n_embd*2` 字节到 `m.h_out16` |

**P2P 路线不动**（这台机不走 P2P；P2P 机器上的字节与行为完全不变）。

### 主卡侧（`src/qwen35/q36_engine.cu`）

| 改动 | 内容 |
|---|---|
| `peer_f16_stage` | device `__half` 中转缓冲（`T*Kp*N`），H2D 的落点 |
| `k_unpack_f32` | 解包核：`src`（fp16）→ `dst`（fp32），写回 `eparts` |
| `PeerPrefill36::wait()` | 多一个参数：主卡侧的中转缓冲（fp16 时用，fp32 时 nullptr） |
| `peer_prefill_wait()` | 把 `peer_f16_stage` 传下去 |

**顺序**：`wait()` 里 H2D（fp16 → 中转缓冲）→ 解包核（中转缓冲 → `eparts` 的 fp32），
两者都在主卡的 `st` 上，顺序天然正确。

## 2. 不变量

1. **行契约不变**：`eparts` 的行数、行序、每行的语义都不变；`eparts` **仍是 fp32**
   （fp16 只存在于传输途中）。`k_moe_out` 读到的值与今天同型。
2. **两个 witness 不能绕过**：所有权交叉核验（`peer_plan` 的专家遍历）与 `rows()` 重复行检查。
3. **P2P 路线不变**。
4. **默认路径逐字节不变**（旗标关时，字节数、核的发射、行的内容与今天完全一致）。
5. **旗标解析**：只认精确的 `"1"`。

## 3. 数值风险（这是唯一真风险）

结果行从 fp32 变 fp16 再变回 fp32 → **数值变了**。fp16 的尾数 10 位（相对误差 ~5e-4），
fp32 是 24 位。

- **溢出**：fp16 的上限是 65504。行里若有更大的值 → inf → NaN 传播。
  **必须先量行内的值域**（或加一个饱和/检查）。
- **精度**：`eparts` 的行是专家输出的加权和，之后 `k_moe_out` 按路由权重再加权求和。
  相对误差 ~5e-4 会传到 logits。

**验收**（缺一不可）：
- 同一 `--force` token 流，fp16 开/关两次 `--dump-full-logits`，逐行比 max|diff|。
  容差：logits 的量级是 ~19（实测 `|logit|max` 10.9–19.0），
  相对误差 5e-4 → 绝对误差 ~0.01 量级。**先量 fp32-vs-fp32 的基线噪声**（同一二进制跑两次），
  再看 fp16 的差是不是同一个量级。
- rc=0、IMA=0、nan=0。
- bench：warm bench 1/2 与 310.2/311.4 比。

**退回条件**：diff 超过容差，或出现 inf/NaN → 退回 fp32 上腿，或退回候选 D（合并下腿 D2H，
不改数值，省 ~1.9 ms/层）。

## 4. 先量值域（实施的第一步）

在打包核之前，先量一行里 `|x|` 的最大值。若远小于 65504，溢出风险为零。
这一量可以用尺子加一个探针（`STRATA_Q36_PROMPT_TIMING` 下多报一个数），
也可以在打包核里顺带算（但那时已经在改了）。
**建议**：实施时在打包核里**同时算 max|x|**（一个原子 max），打印一次 —— 代价 ~0，
但把"溢出风险"从推测变成实测。

## 5. 实施记录（2026-10-23 晚）

**改动文件**：`src/qwen35/q36_peer_prefill.cu` + `.cuh` + `src/qwen35/q36_engine.cu`。

**helper 侧**：
- `m.d_out16`（device `__half`）、`m.h_out16`（pinned `__half`）、`m.d_f16max`（device unsigned）、`m.h_f16max`（pinned unsigned）
  —— **只在旗标开时分配**，默认路径的分配列表逐字节不变。
- `k_pack_f16`：`src`(fp32) → `dst`(fp16)，**同时量出最大的幅值**（`atomicMax` 在 float 的位模式上）。
  值超过 fp16 的上限 65504 时**饱和**（不是变成 inf）。
- `launch()`：fp16 分支 = 打包核 → D2H 传 `n*n_embd*2` 字节。
  P2P 分支**完全不动**。

**主卡侧**：
- `peer_f16_stage`（device `__half`，`tmax*Kp*N` halves = 16 MiB）—— 一次装一个 helper 的行。
- `k_from_f16`：解包回 fp32 写进 `eparts`。
- `PeerPrefill36::wait()` 多一个参数 `void* fp16_stage`：非空 → 行以 fp16 落到 staging，
  调用方在同一 stream 上解包；为空 → 原来的 fp32 直达 `eparts`。
- `peer_wait_base[3]` / `peer_wait_rows[3]`：解包要知道每个 helper 的行基址与行数
  （`peer_plan` 算出来的地方）。

**顺序**（同一条 `st`，FIFO）：
```
helper i: H2D(fp16) → 解包核(→ eparts) → helper i+1: H2D(fp16) → 解包核 → ...
```
staging 一次只装一个 helper 的行，stream 的顺序保证不会互相覆盖。

**遇到的编译错**：`cudaMalloc(&m.d_f16max, ...)` —— `unsigned int**` 不能隐式转 `void**`；
且 `ck()` 的参数不能塞进 `cudaMalloc()` 里。两处都改了。

**已知未接**：打包核量出的最大幅值（`h_f16max`）目前**拷了但没人读** ——
读它要同步 helper 的 stream，代价大于它的价值。改为**由 logits 对照间接证明**：
若有任何值溢出成 inf，`eparts` 会有 inf，`k_moe_out` 求和后 logits 必然出现 inf/NaN 或巨大偏差，
对照会立刻发现。

## 6. 实测（2026-10-23 晚，**MEASURED**）

远端 192.168.1.98，同旗标串，`--bench-pp 512 --bench-tg 0`。
二进制：`bin/strata-q36.parallel-prep` = `7f1ae9f6`（fp32 上腿）、
`bin/strata-q36.upleg-f16` = `165e94b7`（同一个 build，旗标 `STRATA_Q36_PEER_F16=1` 打开）。

| 趟 | fp32 上腿 | **fp16 上腿** | fp16，旗标关 |
|---|---|---|---|
| bench 0 | 203.9 | **214.7** | 205.8 |
| **bench 1（warm）** | **311.2** | **398.1** | **311.3** |
| **bench 2** | **311.5** | **396.1** | **311.3** |

**warm 均值：311.35 → 397.1 tok/s = +27.5%**
**旗标关时（同一个二进制）= 311.3 / 311.3 → 与 fp32 完全一致 → 零影响** ✅
每一趟都 rc=0、IMA=0、nan/inf 行数 0。

**每层时间去哪了（F3，探针开，bench 1，全部 ms/层）：**

| 段 | fp32 上腿 | fp16 上腿 | 变化 |
|---|---|---|---|
| **helper_wait** | **16.434** | **6.975** | **−9.46** ✅ |
| plan | 8.501 | 9.594 | +1.09 |
| primary_work | 8.136 | 8.192 | +0.06 |
| mixer | 7.085 | 7.132 | +0.05 |
| router_route + route_d2h | 0.620 | 0.747 | +0.13 |
| combine + post | 0.250 | 0.251 | 0 |
| **forward** | **41.026** | **32.891** | **−8.14** |

`gpu_residual = 0.000` → GPU 时间线完整闭合。

**为什么省得比估的还多（估 ~5，实测 9.46）**：上腿减半不只缩短了主卡等 helper 的时间，
**helper 自己也更早完成**（它的 D2H 只有一半的字节），所以 `m.ev` 更早满足 ——
两头都省。而 `plan` 涨了 1.09 ms（host 侧的下腿 D2H 占比上升，因为总时间变短了），
净账 −8.14 ms/层。

## 7. 数值：三条独立的证据（2026-10-23 晚，MEASURED）

### 7.1 helper 的算力确实被用上了（**排除"假加速"**）

一个必须排除的可能：若 helper 的行**根本没进 `eparts`**，那么"fp32 与 fp16 的 logits 相同"就只是
**两条路径都没用 helper 的结果**，加速是假的。

判别方法：**关掉 helper 跑一遍**（`--expert-cache-device*` 不给），
与开着 helper 的结果比。

| 对照 | 走的路 | 生成 token | logits 最坏差 |
|---|---|---|---|
| `nohelp`（不给 helper 旗标） | 40/256 专家在 VRAM，其余 **CPU 池** | 与 help 相同 | **max\|diff\| = 0.944** |
| `help`（P4：3 个 helper 接管全部 10240 个专家） | 全部在 helper 上 | — | — |

两条**完全不同的算术路径**（CPU 池的 int8 vs 三个 P104 的 int8），
logits 差 0.944（量级 ~19 → 相对 ~5%），argmax 37/37 行相同。
→ **helper 的行确实进了 `eparts`、确实参与了计算** ✅

### 7.2 fp16 上腿对这个模型无损

| 对照 | 最坏 logits 差 | 结论 |
|---|---|---|
| `help`（fp32 上腿）vs `help16`（fp16 上腿） | **0**（918 万个 float 逐字节相同，0 个非有限值） | 无损 |

生成 token 序列也完全一致。

### 7.3 直接测量打包的代价（探针，`bin/strata-q36.upleg-f16-probe` = `3e9a56a4`）

`k_pack_f16` 在打包的同时量出两件事，engine 每次 bench 打印：

```
strata-q36 PHASE3 bench 1 prompt: the fp16 up leg packed rows up to 18.4533 in magnitude
  (fp16's limit is 65504) and the largest relative error of the round trip was 0
```

- **最大幅值 18.45**，fp16 的上限是 65504 → **溢出风险为零（余量 3500 倍）**
- **最大相对误差 0** → 往返**完全无损**

**为什么是 0 而不是"很小"**：MMQ 的输出是**量化码 × 每专家的 scale**，
而这个 scale 是 2 的幂（或其尾数很短），所以乘积的尾数在 fp16 的 11 位里 → 精确。

**⚠️ 这个结论有范围**：它对**这个模型 + 这个量化 + 这台机器**成立。
换模型或换量化方式，值域和 scale 都可能变 → **所以旗标保留 opt-in**，
而且探针每次都报出实际的幅值与相对误差，换环境时一眼能看出来。
