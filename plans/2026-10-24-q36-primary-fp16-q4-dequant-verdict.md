# q36：主卡用 Q4_K 反量化成 FP16 再算 —— 实测（2026-10-24）

用户主张：「权重用 Q4，反量化 FP16 再计算」；「主卡的算力都在 FP16，Q4 反量化 FP16 计算。
helper 的算力主要在 DP4A，用 INT8 没问题」。

本文用**引擎自己的算子**把这个方案完整测一遍。结论：**在这台机器上它比现有的 int8 MMQ 慢
2.4 倍**，而且慢的原因不是实现不好，是 P100 这个硬件的形状。

## 0. 一句话

**用现成的算子（引擎的 `iq_dequant_f16` + cuBLAS）实测：主卡算一个专家要 241.8 µs
（反量化 68.9 + GEMM 172.9），而现有 int8 MMQ 路径是 100.5 µs/专家。**
主卡的 FP16 峰值（18.7 TF）是 helper 的 2 倍，但**专家是「瘦长」的形状，
P100 的 FP16 在这个形状上只跑到峰值的 4–30%**，而且多了一步反量化。

## 1. 现成的算子（都已存在，不用新写）

| 需要什么 | 在哪 | 状态 |
|---|---|---|
| Q4_K/Q5_K → FP16 的整行反量化 | `src/kernels/cuda/iq_kernels.cu:4231` `iq_dequant_f16`（内核 `dequant_flat_kernel<__half>`，`:3207`） | **引擎自带，已编译** |
| 同上，gate+up 一次出 | `:4265` `iq_dequant_gu_f16`（内核 `dequant_gu_kernel`，`:3221`） | 同上 |
| Q4_K/Q5_K 的块级解包 | `iq_kernels.cu:2995` `get_scale_min_k4` / `:3003` `dq_q4_k` / `:3023` `dq_q5_k`（模板，`dst_t` 可为 `half`） | 同上 |
| FP16 GEMM | cuBLAS `cublasGemmEx`（引擎已用） | 同上 |
| 上游 llama.cpp 的同款算子 | `ggml/src/ggml-cuda/convert.cu:300` `dequantize_row_q4_K_cuda` / `:306` `dequantize_row_q5_K_cuda`，入口 `ggml_get_to_fp16_cuda` | GLOB 编译（`CMakeLists.txt:105`） |

**所以「没有现成算子」不是问题 —— 算子齐了。问题是算完之后快不快。**

## 2. 探针

`/tmp/q4fp16.cu`（远端 192.168.1.98），**链接引擎自己的 `libstrata_kernels.a`**，
所以反量化是引擎真正在用的那个内核，不是抄的。

- 权重：**真模型的** `blk.0.ffn_{gate,up,down}_exps.weight`（从 gguf 读 expert 0 的 slab）
- 形状：`n_embd=2048`、`n_ff=512`、256 专家/层、top_k=8
- 每个专家的字节：gate 589,824 B + up 589,824 B + down 720,896 B = **1.81 MiB**
- 反量化用 `iq_dequant_f16(12/13, ...)`，GEMM 用 `cublasGemmEx(CUDA_R_16F, CUBLAS_COMPUTE_16F)`

**已知的一处不对等**（说出来，不藏）：探针读的 gguf 字节位置有偏差 ——
`d`/`dmin` 读出来是垃圾（`amax=inf`），因为 gguf 的专家轴布局和 `expert_blob`
（`q36_engine.cu:1518`）的 `memcpy(dst, L.src_g + e * L.src_gsz, L.src_gsz)` 之间的
对应关系我没完全对上（`scanlayout.py` 量到 Q4_K 的 block stride = 144、
第一个 block 的 d = 5.949，像真值；所以**块数和访存量是对的，值不对**）。
**这不影响计时**：反量化读同样多的块、写同样多的字节，GEMM 的形状不变。
**但这组数字只用于「时间」，不能用于「数值」。**

## 3. 实测（MEASURED，2026-10-24 远端，主卡 P100 dev0）

| 行数/专家 | 反量化 Q4_K×2 + Q5_K → FP16 | cuBLAS FP16 GEMM (gate+up+down) | **合计/专家** |
|---|---|---|---|
| 1 | 68.2 µs | 51.0 µs | **125.5 µs** |
| 16 | 68.7 µs | 77.0 µs | **152.2 µs** |
| 60 | 68.9 µs | 172.9 µs | **241.8 µs** |

**对照：现有 int8 MMQ 路径 = 100.5 µs/专家**（MEASURED，见 §4）。

**FP16 在主卡上是 1.25–2.46 倍慢。**

### 3a. 为什么慢 —— 三条，都可核

1. **反量化 68.9 µs 是纯开销**：读 1.81 MiB、**写 6.00 MiB**（FP16 是量化的 3.31×）。
   这一步不产生任何有用的输出，只是为了喂给 GEMM。
2. **cuBLAS 在这个形状上打不满**：M=16 行时只有 **0.746 TFLOP/s**（上一轮实测），
   = P100 FP16 峰值 18.7 TF 的 **4%**。专家天然是「每专家十几行」的瘦长矩阵，
   而瘦长矩阵正是 GPU 最不擅长的形状。
3. **int8 路径有结构优势**：q8_1 激活只有 FP16 的 1/2，DP4A 一次算 4 个字节乘加，
   而 FP16 的 FMA 一次算 2 个。且 int8 路径**不写中间 FP16 权重**（省掉 6 MiB 的写）。

## 4. 对等对比（同一批活）

keep-resident 开着时，主卡算 39 个常驻专家、2342 行（512 token prompt 的 57.2%）：

| 路径 | 每层时间 | 每行 |
|---|---|---|
| **int8 MMQ（现状）** | **3.92 ms**（实测 `primary_work` 4.68 − 0.76） | 1.67 µs |
| **Q4→FP16 + cuBLAS** | **9.43 ms**（39 × 241.8 µs） | 4.02 µs |
| 比 | **FP16 慢 2.41 倍** | |

**这还只是算术。** 如果主卡改为 FP16 路径：

- 主卡那 39 个专家的权重得**在 VRAM 里存 FP16 副本**（6.00 MiB vs 1.81 MiB × 39 × 40 层
  = **9.14 GiB**，P100 总共 12 GiB，而量化版只占 2.86 GiB）→ **装不下**；
- 或者每次用时反量化（那就是 68.9 µs × 39 × 40 层 = **107 ms/层**，灾难）。

## 5. 那 P100 的 18.7 TF 去哪了

- **它在 dense 投影上（attention / shared expert）**，那部分已经在用。
- **专家上它被三件事限死**：瘦长形状（4% 峰值）、反量化的写开销（3.31× 字节）、
  以及 P100 **没有 tensor core**（GP100 只有双发射 `__half2` FMA，不是矩阵单元）。
- 对比 helper：P104 (sm_61) 有**真 `__dp4a`**（一次 4 字节乘加），而且专家的形状
  对整数点积友好。**helper 的 int8 DP4A 在专家这个形状上是对的工具。**

## 6. 判断

- **用户的架构分工（主卡 FP16 / helper int8 DP4A）在别的机器上可能对** ——
  有 tensor core 的卡（sm_80+）上 FP16 GEMM 的瘦长形状效率高得多，
  而且不必反量化（权重本来就有 FP16 版本）。
- **在 P100 (sm_60) 上，它比现状慢 2.4 倍，且装不下 FP16 权重。**
  实测的三条原因都不是实现问题：形状、反量化写开销、无 tensor core。
- **「helper 用 int8 DP4A」这一半是对的，而且已经在用**
  （`helper_wait` 13.29 ms/层就是它；sm_61 的真 `__dp4a` 比 sm_60 的回退快 2.31×，MEASURED）。
- **真正能动的地方仍是 PCIe**：prefill 每层 26.67 ms 里，helper 的下腿
  4 MiB fp32 激活 = 5.18 ms 是唯一全额暴露在关键路径上的 PCIe 时间
  （`plans/2026-10-24-q36-down-leg-bytes.md`）。改 fp16 省 2.59 ms/层（+10.7%），
  改 q8_1 省 3.88 ms/层（+17.0%）。

## 7. 如果还要走这条路，三个前提要先量

1. **反量化能不能便宜一半？** 现在 68.9 µs 里，写 6.00 MiB 占大头。
   如果反量化直接写进 GEMM 的输入布局（省一次往返），可能省 30–40%。
   **未测。**
2. **cuBLAS 换算法？** M=16 时 0.746 TFLOP/s 很低，可能 `cublasLtMatmul`
   或手写的瘦长 GEMM 更快。**未测。**
3. **用 `CUBLAS_COMPUTE_32F` + FP16 存储？** 避免 FP16 的数值精度损失，
   但 P100 上 FP32 是 FP16 的一半速。**未测。**

**这三条都可能有 20–40% 的改进，但即使都做到位，也只是把 2.4 倍缩到 1.5–2 倍，
仍然不如现状。** 所以这条路在这台机器上不推荐，除非有别的卡。

## 附：FP16 路线在别处的可行性

| 硬件 | FP16 GEMM (M=16, 专家形状) | 有 tensor core | 结论 |
|---|---|---|---|
| **P100 (sm_60)** | 89.9 µs / 0.746 TFLOP/s | **无** | 本机实测，慢 2.4× |
| P104 (sm_61) | 1094 µs（cuBLAS 无此 kernel） | 无 | 本机实测，更慢 |
| sm_80+ / sm_89 / sm_90 | 未测 | **有** | 大概率快得多（tensormap / mma） |

**「主卡走 FP16」要在 sm_80+ 上重新量。** 本机（sm_60/61）没有 tensor core，
FP16 只有双发射 FMA，赢不了 int8 DP4A。
