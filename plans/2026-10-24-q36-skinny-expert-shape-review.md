# q36：专家的瘦长形状 —— 复核与优化（2026-10-24）

复核「形状：专家天然瘦长，M=16 行时 cuBLAS 只到 0.746 TFLOP/s = P100 FP16 峰值的 4%」，
量「如何优化」，并回答「DP4A 有没有同样的填不满问题」。

**三句话结论**

1. **0.746 TFLOP/s 这个数是错的**（探针漏算一个投影 + 权重布局错）。正确值 M=16 是
   **1.126 TFLOP/s = 峰值 6%**，M=60 是 4.269 TF = 23%。「4%」站不住。
2. **归因也错**：不是形状天生吃亏，是**一次只算一个专家，GPU 填不满**。
   把 39 个专家打包进一次 launch，M=60 时从 553 µs/专家降到 **88.4 µs/专家**（6.3 倍）。
   **但权重读带宽仍只有 71–95 GB/s（HBM 上限 732 的 10–13%）—— 打包后依然填不满。**
3. **DP4A 有完全一样的问题**，而**引擎已经修好了它**（16 专家分组 + stream-k，
   `moe_mmq.cu:531` 目标 ≥90% tile 效率）。FP16 路径要跟上，缺的就是这套调度。

## 0. 先更正前一轮的三个错

| | 之前（错） | 现在（实测） |
|---|---|---|
| M=16 FP16 全专家 | 152.0 µs / 0.662 TF | **89.4 µs / 1.126 TF** |
| 「cuBLAS 只有 0.746 TF = 4%」 | 引用 | **1.126 TF = 6%**（M=16）；M=60 是 **4.269 TF = 23%** |
| 「打包后 726 GB/s，到 HBM 上限」 | 我上一轮说的 | **95 GB/s，13%** —— 探针 grid 越界，那个数是假的 |

前两个错来自 `q4fp16.cu`：
1. 计时循环里 `gemm_gu` 只对 gate 调了一次，**`up` 投影的 GEMM 从没执行**，
   标签却写「gate+up+down」—— 少算 1/3 算力。
2. 权重布局用错：`OP_T` 配 `lda=FF`，而 gate 的 slab 是 `[FF][K]` 行主序，
   `OP_T` 需要 `lda=K`。错的布局让 cuBLAS 走更差的访存路径。

第三个错是我这次探针自己的：grid 算成 `E * (N/8)` 但 block 没按专家索引，
**读越界了**（没崩，但时间是假的）。修正版用 `grid = (N/8, E)`，`blockIdx.y` 是专家。

**教训**：同一件事量三遍才稳。前两轮的数都不能用。

## 1. 真正的机制：不是形状，是并行度

P100，M=16，完整专家（gate+up+down），FP16 权重，cuBLAS（`probe4`）：

| 一次 launch 的专家数 | 每专家 | 权重读带宽 | TFLOP/s |
|---|---|---|---|
| 1 | 89.42 µs | 70.4 GB/s | 1.126 |
| 4 | 79.16 µs | 79.5 GB/s | 1.272 |
| 16 | 68.38 µs | 92.0 GB/s | 1.472 |
| **39** | **66.19 µs** | **95.0 GB/s** | **1.521** |

M=60：

| 一次 launch 的专家数 | 每专家 | 权重读带宽 | TFLOP/s |
|---|---|---|---|
| **1** | **553.20 µs** | 11.4 GB/s | 0.682 |
| 4 | 126.1 µs | 50.1 GB/s | 2.998 |
| 16 | 89.9 µs | 69.9 GB/s | 3.741 |
| **39** | **88.41 µs** | **71.2 GB/s** | **4.269** |

**M=60 时打包给 6.3 倍**（553 → 88.4），**M=16 时只给 1.35 倍**（89.4 → 66.2）。
差别在于 M 越大，能切出的 tile 越多，单专家就越能自己填满。

**但即使打包到 39 个专家，带宽也只有 95 GB/s = HBM 的 13%。**
所以「填不满」这件事**打包只解决了一半**：

- M=16：M 太小，单个专家的输出（512×16）切不出多少 tile → 靠打包解决。
- 剩下的：**算术量本身就小**。M=16 时一个专家只有 100.66 MFLOP，
  按 18.7 TF 算要 5.4 µs；而 6.00 MiB 权重读一遍要 8.6 µs。
  **理论下限约 8.6 µs/专家**，实测 66.19 µs —— 还有 7.7 倍的空间，
  但这 7.7 倍不是「形状」造成的，是**cuBLAS 在这个形状上不擅长**。

## 2. 排除「换个 cuBLAS algo 就能修」

`fp16algo.cu` 扫了全部 24 个 algo id（M=16，gate 形状，FP32 累加）：

```
algo  0 DEFAULT          28.40 us      73.8 GB/s   <- 最好
algo 13/14/15            57.68 us      36.4 GB/s
algo 16/17             52.05/51.44us 40.3/40.8 GB/s
algo  2..6              158..487 us
```

**DEFAULT 已经最优**，换任何一个都更慢。

### 排除「1Cat 的 V100 做法能修」

1Cat-vLLM 的 V100 生产路径（`csrc/attention/sm70_79t/prefill.cu:1969-1995`）用
`CUBLAS_GEMM_ALGO9_TENSOR_OP` + **FP16 alpha/beta**（FP16 累加）。
在 P100 (sm_60) 上复现（`fp16lt.cu`）：

| 累加方式 | 最好 algo | 用时 | ALGO9 |
|---|---|---|---|
| FP32 alpha, COMPUTE_32F（引擎 `prefill/gemm.cu` 现在的做法） | 0 (DEFAULT) | 33.89 µs | 65.22 µs |
| FP16 alpha, COMPUTE_16F（1Cat 的 V100 选择） | 0 (DEFAULT) | **31.17 µs** | **unsupported** |
| FP16 alpha, COMPUTE_32F | 0 (DEFAULT) | 30.91 µs | 63.81 µs |

- ALGO9 在 P100 上要么慢 2 倍，要么（COMPUTE_16F）**根本不支持**；
- FP16 累加只快 **8%**（31.17 vs 33.89 µs），而它**改变数值**（FP16 累加 2048 项）。

**1Cat 的 V100 优化不可迁移到 P100。** V100 有 tensor core，ALGO9_TENSOR_OP 有意义；
P100 (sm_60) 没有。

## 3. DP4A 有没有同样的问题：有，一模一样

**P100 (sm_60)，手写 dp4a GEMV，N=512 K=2048，int8 权重**（`dp4afill.cu`）：

| 一次 launch 的专家数 | M | 每专家 | 权重读带宽 | 离 HBM 上限 | block/波 |
|---|---|---|---|---|---|
| 1 | 1 | 5.13 µs | 204.5 GB/s | 3.6× | 64 / 1.14 |
| 1 | 16 | 59.13 µs | **17.7 GB/s** | **41.3×** | 64 / 1.14 |
| 1 | 60 | 302.85 µs | 3.5 GB/s | 211× | 64 / 1.14 |
| **16** | **16** | **3.70 µs** | **283.5 GB/s** | **2.6×** | **1024 / 18.29** |

同一形状、同一打包度，把 int8 和 FP16 摆在一起（`probe3` / `probe5`，
M=16，gate 一段，E=39 一次 launch）：

| | 每专家 | 读的权重 | 字节效率 |
|---|---|---|---|
| int8 dp4a（Q4 尺寸的 stand-in） | **17.43 µs** | 0.56 MiB | 32.3 MB/µs |
| FP16 cuBLAS | 22.33 µs | 2.00 MiB | 89.6 MB/µs |
| FP16 手写 GEMV（`probe2`） | 27.39 µs | 2.00 MiB | 73.0 MB/µs |

**FP16 的每字节效率高 1.9–2.8 倍，但需要 3.31× 的字节。**

### 但引擎的 int8 路径**已经修好了这个问题**

`src/prefill/moe_mmq.cu` / `mmq_resident_sort.hpp`（远端读源码确认）：

- 一次 launch 处理**满 16 个专家**（`STRATA_MMQ_GROUP_SORT`），
  按 token 数排序把工作量相近的专家放一起；
- **stream-k** 切分，目标是 **≥90% 的 tile 效率**
  （`moe_mmq.cu:531` 的注释：按 SM 数算波数，`100*tiles/(nsm*waves) >= 90`）；
- tile 数按 `tiles = per_ntx * ntx` 算，block 固定 256 线程。

**所以「int8 的 DP4A 填不满」在引擎里不是问题。**
我上面手写的单专家 kernel 只是为了**量化「填不满」这件事本身**，
它不代表引擎的做法。

**结论：FP16 路径要跟上，缺的不是新算法，是把 MMQ 那套调度（16 专家分组 + stream-k）
套到 FP16 算子上。** 这不是新发明。

## 4. 融合反量化（1Cat 的核心手法）

1Cat 的 AWQ kernel（`benchmarks/csrc/sm70_awq_m5_batched_gemv.cu`）的真正做法：
量化权重**只读一次进寄存器**，用 `lop3` 魔数（`:90-123` 的 `convert_u4x8_to_half`）
转成 half2，scale 和 zero-point 用 `__hfma2` 折进去（`:202-204`），
乘加在同一个循环里，**从不写回内存**。

我照着做了一版 Q4_K 融合 GEMV（`q4fused.cu`）：**17.02 µs/专家**（16 专家打包，gate 一段），
比 FP16 权重版（22.33 µs）快 1.3 倍。方向对。

**但我的实现不够好**：用标量 float FMA、没走 `__hfma2` 的双发射、
没实现 `lop3` 魔数（它一次 `lop3` 转 4 个 half2）。还有优化空间。

**这条路的价值在于 VRAM**：FP16 权重要 3.31× 的空间，融合反量化让 VRAM 里只放 Q4。
见 §5。

## 5. 还剩的三个前提（未测）

1. **VRAM 装得下吗？** 主卡常驻 39 专家/层 × 40 层：
   - FP16 副本 = 39 × 40 × 6.00 MiB = **9.14 GiB**（P100 共 12 GiB）
   - Q4 = 2.86 GiB
   - **差 6.28 GiB。** 装不下，除非减主卡专家数（更多下放 helper），
     或走 §4 的融合反量化（VRAM 只放 Q4）。
2. **主卡那 39 个专家是谁选的？** 换 FP16 副本后能装几个，决定 helper 接多少。**未量。**
3. **数值影响。** FP16 权重 + FP16 算 vs Q4_K 权重 + int8 算，logits 差多少？**未测。**
   「a wrong answer is worse than a failed run」。

## 6. 那 FP16 到底划不划算

把字节账摆出来（这是决定性的，因为 prefill 的墙是 PCIe 不是算力）：

| | 主卡算一个专家 | 走 PCIe 到主卡 |
|---|---|---|
| int8（Q4 权重，helper 算） | 17.43 µs（打包后，M=16 gate 段） | 1.81 MiB @ 6.07 GB/s = **313 µs** |
| FP16（副本常驻主卡） | 66.19 µs（打包后，全专家 M=16） | 0（不用传） |
| FP16（融合反量化，Q4 住主卡） | 22.33 µs 级 + 融合开销 | 1.81 MiB @ 6.07 GB/s = **313 µs** |

**PCIe 传一次专家（313 µs）比在主卡上算它（22–66 µs）贵 5–14 倍。**
所以规则很清楚：**专家权重一旦要过 PCIe，就在 helper 上算（int8 划算）；
要留在主卡算，FP16 副本比每次重传便宜得多。**

**主卡该放 FP16 副本的专家 = 那些 PCIe 传不动的（常驻的）**，
这正好和「helper 用 int8 DP4A」是同一件事的两面。

**但前提是 FP16 副本装得下（9.14 GiB / 12 GiB，几乎占满）**，
而且 PCIe 侧本来就已经是墙（见 `plans/2026-10-24-q36-down-leg-bytes.md`，
下腿 fp32→fp16 省 2.59 ms/层 = +10.7%）。

## 7. 建议的下一步

按依赖排序：

1. **先做分组，不碰算法。** 主卡 39 个专家打包成一次 launch
   （照搬 MMQ 的 `mmq_resident_sort` + stream-k 结构，换成 FP16 算子）。
   预期 M=60 时主卡专家算术 553 → 88 µs/专家。**但带宽仍只有 71 GB/s，
   离 8.6 µs 的理论下限还差 10 倍** —— 所以这一步不是终点。
   旗标 `STRATA_Q36_PRIMARY_F16=1`，默认关，默认路径逐字节不变。
2. **解决 VRAM。** 融合反量化（Q4 在 VRAM，寄存器里反量化）。
   1Cat 的代码给了完整蓝本（`lop3` 魔数 + `__hfma2` + warp shuffle）。
3. **数值验证。** logits 逐行对照，argmax 一致数 + max|diff|。
4. **PCIe 独立可做。** 下腿 fp32 → fp16/q8_1（+10.7% / +17.0%），
   和 FP16 无关。

**skip: 在 P100 上找 cuBLAS 的「更好的 algo」—— 24 个扫完，DEFAULT 最优；
skip: 照搬 1Cat 的 ALGO9_TENSOR_OP —— P100 上要么慢 2 倍要么 unsupported；
skip: 以为 P104 能做 FP16 —— cuBLAS 在 P104 上没有这个形状的 kernel（1094 µs），
helper 只能走 int8；
skip: 「打包一次就填满了」—— 打包后带宽仍只有 HBM 的 13%，还差 7.7 倍。**
