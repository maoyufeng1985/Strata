## 1. 为什么（MEASURED，2026-10-25，--mtp 3，marshal 开，tg64 文本）

`STRATA_Q36_MTP_TIMING=1`（三个 cudaEvent：步开始 / MTP 层结束 / 草稿头结束）：

| 样本 | 层 | 草稿头 | 合计 |
|---|---:|---:|---:|
| 链式草稿步（1 行）| 1.458 ms | 1.267 ms | 2.725 ms |
| 每窗的 prep（MTP 块跑 D+1=4 行）| 3.572 ms | 1.275 ms | 4.847 ms |

**草稿步里层占 54%，草稿头占 46%。** 而草稿头那 515 MiB 的 Q8_0 已经跑到
433 GB/s（P100 规格带宽的 79%），头这边没有空间了。

**层那 1.458 ms 是谁？** MTP 块自己那一层（第 41 层）的专家**不在任何一张卡的 VRAM 里**：
- 主卡每层只留 40/256 个专家的槽（`hybrid experts: 40 of 256 per layer in VRAM`），
  那 40 个槽分给 40 个主层，MTP 块那一层一个都没有；
- helper 的缓存只有 40 层（`open_helpers` 的 ranked 只到 `l < g.n_layers`）。

⇒ **MTP 块那一层的 8 个 entry 全落到 CPU 池**：解码时 CPU 池一个专家都不算
（报告 "0 on the CPU pool"），MTP 一跑就变成 "14265 on the CPU pool in 1252 ms"。
草稿步那 1.458 ms 的层，主要就是 CPU 池在算这 8 个专家（一个 entry 一步，串行）。

**（更正：CPU 池剩下的那 1166 ms 是提示词那 50 行的——50 行超过 helper 的 MAXT，
所以提示词那一窗没走 helper，落到 CPU 池上；它不在 MTP 的关键路径上。）**


## 2. 改什么

1. `open_helpers`：布局表加上 MTP 块那一层（41 项，`expert_layout_set_native` 的检查只是
   `fmt.size() == n_layers`），helper 的 `open` 传 `layers = 41`，`claimed` 也是 41×256。
2. row split 的 ranked：每个 helper 多拿 MTP 块那一层里 `e % n == k` 的专家，
   **放在列表最前**（`auto` 的 helper 装不下时是从列表末尾停的，MTP 层正是这个旗标要的）。
3. `helper_layer(li)`：`li == n_layers` 时只有旗标开才算真。
4. 旗标要 `STRATA_Q36_HELPER_PARALLEL=1`（stripe 那套按层查表，MTP 块不在任何 stripe 里）。

VRAM：每张 helper 多 85 个专家 × 1.88 MiB ≈ 160 MiB（每张现在 5.14 GiB，8 GiB 装得下）。

**数值会变**：helper 的 grouped kernel 和 CPU 池是两套实现（主层上也是这两套），
所以草稿提议会变、接受率会动。commit 出来的文本是 verify 窗定的，通常不变——
**这是要量的，不是要假设的**。

## 3. 怎么量（门）

- `STRATA_Q36_MTP_TIMING=1` 的层时间（1.458 ms → ?）
- `--mtp 3` 的 tok/s（80.3 → ?）和 MTP-DEPTH 的每深度接受率
- 旗标关：文本与旗标开之前**逐字节相同**（默认路径必须不动）
- 旗标开：文本大概率不变，但**要对比并如实写**

`rt/draft_vocab.bin` 那种按频率挑的 token 列表），不是「前 N 个 token id」。

**⇒ 草稿头这条路是死的**（除非有一份好的子集表）。MTP 要提速只能动那 1.458 ms 的层。
