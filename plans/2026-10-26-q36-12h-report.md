# Q36 的 12 小时优化：做了什么，测到了什么（2026-10-26 → 10-27）

给用户的成果报告。每个数都带它是在哪台机器、什么配置下量到的；
没有量到的写「未测」，静态分析写「读代码」。

## 0. 一句话

- **十个提交落地**：GQA 自动开关（32K 上 decode +50%）、Quest 的选择 pass 重写（同 k 下 +29%）、
  `--tokens-file`（长 prompt 的 id 塞不进 argv）、Quest 的计时探针（+ 它自己会打印了）、
  mixer 的每层 CUDA 图、文档修正。
- **rebase 到上游**：92 个本地提交重放到 `origin/main`（上游领先 577 个提交），
  `src/qwen35/` 上游 **0** 个提交 ⇒ q36 引擎逐字节未变。
- **两个结论被实测推翻**（这轮最有价值的东西）：
  1. **decode 不是主机受限的**。把主机那段入队时间真的拿掉（mixer 每层 202.8 → 9.0 µs），
     decode 的墙钟**一点没动**（60.6 vs 60.3 tok/s）⇒ 卡住的是 GPU 的活和 helper 的 PCIe。
  2. **Quest 的 13 ms 不在选择 pass 上**。探针实测：bounds + select 只花 **0.503 ms/token**，
     而且与 k 无关 ⇒ 那 12.9 ms 在 Quest 路径的 attention 侧 ⇒
     「把选择 pass 压到 1 ms」这条下一步作废。

## 4. Quest 的选择 pass 重写（`R-questfast`）

同一个盒（P100-12GB + 三个 P104-100），peer 路径全开，`--kv int8`，
`--bench-pp 32768 --bench-tg 64`，ctx 40960：

| 档 | 二进制 | tg64 |
|---|---:|---:|
| 稠密（GQA 关）| 旧 | 34.4 |
| 稠密（GQA 关）| **新** | **34.3**（默认路径逐位同档 ✓）|
| Quest k=8（GQA 关）| 旧 | 42.0 |
| Quest k=8（GQA 关）| **新** | **54.0（+29%）** |
| Quest k=1024（GQA 关）| 新 | 23.7 ⇒ **选择 pass 的固定成本 13.0 ms/token** |
| GQA=auto（稠密）| 新 | 51.8 |
| GQA=auto + Quest k=8 | 新 | 53.2（只 +2.7%）|

**改了什么**（三个都只动 Quest 开着时走的代码）：

1. **页内最大的 group scale 提到写页的时候算**（`k_quest_bounds`）。它只依赖 (页, KV head)，
   八个 query head 共用一页 ⇒ 旧写法把同一页的 1024 个 scale 扫了八遍，每层每 chunk 八遍。
   `max` 是精确的 ⇒ 值一模一样。
2. **chunk 循环拆到多个 block**（grid `(nblk, nt*H)`）。一个 token 只有 16 个 row，
   旧 grid 是 16 个 block，P100 的 56 个 SM 只用了 28%；现在 32k 上是 4×16 = 64 个 block。
3. **top-k 单独一个核**（`k_quest_pick`）。逻辑一字未改（同样的「严格大于才换 best」⇒ 并列时选中的也一样）。

⇒ **分数逐位不变**（dim 的归属、warp 归约的顺序、8 个 warp 总和的顺序都没动）
⇒ **选中的 chunk 相同** ⇒ 输出相同。

## 6. mixer 图（`STRATA_Q36_MIXER_GRAPH=1`）

**做什么**：decode 的每一层，mixer 的那十几个核（GDN 或 attention 分支、投影、conv、路由、top-k、add_rms）
先 capture 成一张 CUDA 图，之后每一步重放这张图。**四十次 graph launch 换掉四十乘十二次 kernel launch。**

**为什么能这么做**：mixer 的核**与路由无关**——每一步都是同样的核、同样的形状；
路由的结果只决定「层与层之间主机读什么、helper 算什么」，不影响 mixer 自己算什么。

**为什么不能整个 forward 画一张**：层与层之间主机要把路由读回来给 helper，
那里还有一次 `cudaStreamSynchronize` ⇒ capture 里是非法调用。所以只能**每层一张**。

**三个坑（都是读代码读出来的）**：

1. **图不能画成「整个上下文的 chunk 数」**。mixer 的 chunk 数 `nc = min(n_chunk, ceil((pos+1)/256))`
   随位置变，而且 **GQA 自动规则读的就是这个数**（`nc*256 >= 2048` ⇒ 用共享形状，否则用老 kernel）
   ⇒ 用整个上下文的 `n_chunk` 画图，会烤进一个 eager 路径当时**不会选**的 kernel 形状 ⇒ 数值就变了。
   ⇒ 改成**照 eager 的 grid 画**，并且**chunk 数一变就丢掉重画**（每 256 个位置变一次）。
   证：300 token 的那趟 parity（位置从 32 走到 332，跨过 256 的坎）里，
   引擎报 **80 张图**（40 层 × 2 次 capture），token 仍与 eager 逐字节相同。
2. **图是按 (session, layer) 存的**：mixer 的 K / V / GDN 状态指针是 session 的（`load_cur` 会换指针）。
3. **在第 2 个 decode step 画**：第 1 步是这些 kernel 的第一次使用（MMQ/MMVQ 的工作区那时才分配），
   capture 里 `cudaMalloc` 是非法的 ⇒ 第 1 步画必然失败。

**还有一件要核对的事**：capture 会把主机的分支烤进去（`xq_ready`：prep_in 走「量化」还是「复用上一层留下的图」——
这两条路的**不是同一批字节**；`xq_post`：图是不是已经写好了）。
所以 replay 时先核对主机状态，不一致就**这一层这一步走 eager**，图留给别的层用。

**旗标**：`STRATA_Q36_MIXER_GRAPH=1`（opt-in）。不设旗标时，一个字节、一个核都不变。

**parity 门**（同一个 prompt，有图 / 无图）：

| 测法 | 结果 |
|---|---|
| 8 个 token，默认形状 | **逐字节相同** ✓ |
| 300 个 token（跨过 256 的坎 ⇒ 图重画一次）| **逐字节相同** ✓ |
| 300 个 token，GQA 自动形状 | **逐字节相同** ✓ |

**主机的账**（引擎自报，300 token 那趟）：

| | µs / 层 |
|---|---:|
| **图的重放（一次 `cudaGraphLaunch`）** | **9.04** |
| eager 的 mixer（十几次 kernel launch）| 202.8 |

⇒ **主机的入队成本降到 1/22**（9.04 vs 202.8 µs）。
⇒ 40 层 ⇒ 每 token 省 **7.4 ms** 的主机时间（7.63 → 0.34 ms/token）。

**速度**（peer 路径全开，`--bench-pp 512 --bench-tg 64`，ctx 2048，`--kv int8`；三次 bench 取平均）：

| | eager | 有图 |
|---|---:|---:|
| 主机的 mixer（µs/层）| 202.8 | **9.0**（-95%）|
| **tg64（tok/s）** | **60.6** | **60.3** |

**⇒ 主机的入队成本降到 1/22，decode 的墙钟一点没动。**

| | eager | 有图 |
|---|---:|---:|
| 32K（`--bench-pp 32768`，ctx 40960）| 34.4 | 34.5 |
| 32K + GQA 自动（`STRATA_Q36_ATTN_GQA=a`）| 51.7 | 51.6 |

（每一档都确认图真的在用：引擎自报 40 张图、每层 8.8–9.1 µs，而 eager 是 135–227 µs。）

**⇒ 这推翻了 §5 的判断：decode 不是主机受限的。**
主机的 mixer 入队时间（7.63 ms/token）和 GPU 自己的活、helper 的 PCIe 往返**是重叠的**，
真正卡住的是后两个。**GPU 时间线的那个「空档 4.20 ms」不是等主机，是等 helper 的结果。**

⇒ **下一个杠杆不是主机，是 GPU 的活和 helper 那条 PCIe**（见 §9）。
⇒ 这个旗标本身是有用的（主机的成本降 15 倍，字节不变，默认关闭）：
一旦 GPU 更快、或者多个 session 共用主机，主机就会变成新的天花板。


## 7. Quest 的 13 ms 花在哪：**不在选择 pass 上**（探针实测）

上一版报告说「选择 pass 的固定成本 ≈ 13 ms/token」，那是从
「k=1024（全部保留）比稠密慢 13 ms」减出来的。**这次用引擎自带的探针（每层四个 event）量了每个核**，
结论和那句话不一样：

| 档 | tg64 | 探针 |
|---|---:|---|
| 稠密（Quest 关）| 34.5 | — |
| **Quest k=8（6% 保留）** | **53.7** | **bounds 0.095 ms/token，select 0.408 ms/token** |
| Quest k=1024（全部保留）| 23.6 | bounds 0.103，select **0.408**（和 k=8 一样）|

⇒ **选择 pass（bounds + select）只花 0.503 ms/token**，而且**和 k 无关**（k=8 和 k=1024 一样）。
⇒ **那 13 ms 不在选择 pass 上**：k=1024 档比稠密慢 13.4 ms/token，
而它的 bounds+select 和 k=8 一样是 0.5 ms ⇒ **12.9 ms 在 Quest 路径的其他地方**
（attention 侧带掩码的那条路，或者 top-k 那个核——**探针目前只印 bounds 和 select，
没印 pick 的时间**（`q_ev[2]→q_ev[3]` 那一段没进报表），这是探针的一个缺口）。
⇒ **所以「把选择 pass 压到 1 ms 以下」这条下一步作废**：它已经是 0.5 ms 了。
⇒ **真正的下一步**：查 Quest 路径上那 12.9 ms（attention 侧）——
这同时解释了「GQA + Quest 反而是负收益」（GQA 已经把流量降了 8 倍，
Quest 省下的带宽抵不过它自己在 attention 侧的成本）。

## 8. MTP：MTP 那一层的专家该放哪（`R-mtphelper2`）

`--bench-tg` 看不见 MTP（它画随机 id，draft 永远不中）⇒ 用真实 prompt 的墙钟量：
256 个 token，`--mtp 3`，ctx 4096，peer 路径全开，192.168.1.98。

| MTP 那层的专家放哪 | prompt 0 的墙钟 | prompt 1 的墙钟 | d=2 的接受率（prompt 0）|
|---|---:|---:|---:|
| **留在主卡（`STRATA_Q36_MTP_VRAM=1`）** | **96.7 s** | **103.4 s** | **71.8%** |
| 放 helper（`STRATA_Q36_MTP_HELPER=1`）| 104.6 s | 105.8 s | 68.1% |
| 放 CPU pool（默认）| 102.6 s | 103.0 s | 68.1% |

⇒ **留在主卡最快**（helper 那条多 8%，CPU pool 多 6%），**而且 draft 的接受率最高**
（71.8% vs 68.1%：helper 和 CPU pool 用的是另一个实现，draft 会差一点点）。
⇒ 代价是主卡每层少 5 个专家的槽（33 而不是 38），prompt 要多付一点——
在 prompt 32768 那个量级上，这笔交换仍然是赚的（96.7 s 里含 prompt）。
⇒ **MTP 的层要留在主卡上**；`STRATA_Q36_MTP_VRAM=1` 是这件事的开关。

## 9. 还没做的（按预期收益排）

1. **Quest 路径上那 12.9 ms/token**（§7）：不在选择 pass 上（那里只有 0.5 ms），
   在 attention 侧 ⇒ 查它才能让 Quest 在 GQA 之上也变成正收益。
   顺带：探针的报表还漏了 pick 那个核的时间（`q_ev[2]→q_ev[3]` 没进报表），要补。
2. **decode 的 GPU 侧和 PCIe**（§6 之后才知道的）：主机的入队不是瓶颈。
   **（2026-10-27 整条重核过，三个数都改了 ⇒ 详见 `plans/2026-10-27-q36-decode-next-lever.md`。）**
   三个大块在**不同的资源上，不能相加**（3.7 那块在 mixer 的 5.65 ms GPU 段里面，
   helper 的 4.24 ms 与 GPU 的活是重叠的）⇒ 墙钟是重叠部分的最大值：
   - **attention 的读**：默认核 **14.3 ms/token**（探针实测，32K decode cell；
     GQA 共享核 **4.8 ms/token**）⇒ 32K 的墙钟是 28.8 ms/token（默认核）/
     **19.3 ms/token（GQA 共享核，+50%）**。**原来的「约 25 ms/token」没有测量支撑**，
     探针实测是 14.3（默认核）。
   - **helper 的往返**：**4.24 ms/token**（ctx 2048 那趟），**纯传输只有 0.04 ms**
     （每 token 下行约 100 KiB）⇒ 是**同步税**（3 条 helper 流上的阻塞
     `cudaStreamSynchronize` + 主机 scatter），不是带宽 ⇒ 少字节没用，要少同步。
     （链路的实测带宽：H2D/D2H 都是 0.79~0.81 GB/s，gen1 x4，上限 ~1.0 GB/s；
     **0.58 GB/s 是 prefill 那条 peer 路径的下行，对 decode 没有解释力**。）
   - **dense GEMV 的地板**：**3.7 ms/token**（1.51 GB dense 权重 ÷ 410 GB/s）——
     注意是 **dense（非 routed）**，不是「专家」；routed 专家（580 MiB/token）在当前 peer
     配置里 88% 在 helper 上 ⇒ 已经算在 helper 那条里 ⇒ 单列一条是重复计数 + 归错地方。
   ⇒ **下一个杠杆是 attention 核的并发度**（流量已经砍到 1/8，只换来 3.03 倍的时间），
   不是 PCIe 字节。
3. **ctx 262144 的 KV 装不下**：int8 KV 2.84 GiB + staging 1.10 GiB > P100 的 12 GB
   ⇒ 要么 KV 流式，要么搬上游的 Q4_0 旋转 KV（144 B/head/cell，**省显存，不是提速**）。
4. **MTP 那一层的专家要留在主卡**（§8 已量），别的走法都更慢。
5. **上游的 `src/kernels/cuda/kv_q4.cu`**（Q4_0 + FWHT256 的 KV）两棵树都没接进 q36 ⇒ 是新活，不是 cherry-pick。

## 10. 这次踩到的两个坑（都写进了 `plans/2026-10-26-q36-12h-plan.md`）

- **build 的产物在 `build/strata-q36`，不在 `bin/strata-q36`**（后者是 10 月 22 日的旧二进制，没人往那儿拷）。
  拷错 ⇒ 测的是一个没有这个旗标的旧引擎 ⇒ 「旗标没有加速」是个**假的结论**。
  ⇒ 每次测完先 `strings bin/strata-q36.X | grep -c '<只有新代码才有的字符串>'`，是 0 就是旧二进制。
- **旗标没生效时，测量脚本不会报错**：它照样跑、照样出数。
  ⇒ 每次 A/B 都要先看「新代码的那行字有没有出现」（本报告里的 capture 计数就是干这个的）。
