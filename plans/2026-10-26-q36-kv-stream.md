# q36 的 KV 放主机内存、显存只留滑窗（2026-10-26）

## 账（已算 + 实测，MEASURED 2026-10-26）

- Qwen3.6-35B-A3B，40 主层 + 1 MTP；**11 个全 attention 层**（`layer % 4 == 3` 是 10 层，加 MTP），
  2 KV heads，head_dim 256。**（这行早先写的"13 个"是错的，40 层里 `%4==3` 是 10 层。）**
- `--kv int8` 在 262144 ctx 下 KV = **3.30 GiB**；2048 ctx 下 0.03 GiB。
- 主卡 P100 12 GB（**CUDA ordinal 0**；nvidia-smi 的 index 2 才是它，index 0 是 P104）：权重 4.40 GiB，
  ctx 2048 时 free 4.70 GiB，专家 38 slot/层（2.78 GiB），staging 1.10 GiB。

**262144 ctx 今天直接跑不起来（MEASURED）**：

```
strata-q36: context 262144 cells, prompt chunk 2048, KV cache K int8 / V int8, MTP block loaded, 0.81 GiB of VRAM free
strata-q36: not enough VRAM left for the hybrid experts' buffers and slots
  (1256 MiB needed, 832 MiB free after the weights, the context and the sessions)
```

⇒ 4.70 GiB → 0.81 GiB，KV 吃掉了 3.89 GiB。**KV 流式是这条路唯一的解**（或者 KV 换更小的格式）。

## 目标

KV 全量放 pinned host 内存，VRAM 只留一个 8192-cell 的滑窗（0.10 GiB），省出 **3.20 GiB**
⇒ 主卡专家从 38 变成约 **81 slot/层**（2.78 → 5.93 GiB），262144 ctx 才跑得起来。

## **这条路不成立（MEASURED 2026-10-26）：q36 的 attention 是稠密的**

> ⚠️ **这段只否定了 KV 流式这条路，不是在说「q36 的 attention 改不动」。**
> 同一份计划后面量到：**GQA 共享形状把同一份 KV 的读取次数降了 8 倍**（逐位不变，32K 上 decode +50%，
> 见下面的「GQA kernel」），Quest 又在它上面做训练无关的稀疏选择。
> 「稠密 attention 必须读全部 cell」这个事实没变 ⇒ **KV 流式这条路仍然不成立**；
> 但「q36 的 attention 只能稠密」这句话已经过时了。

Flash-Next 的 `kv_stream.cu` 是为**稀疏 QSA** 设计的：`kv_stream_resolve` 只拉**选中的** block
（每层 `idx_top_k = 2048` cell = 512 block）。q36 不用 QSA——它读**每一个** cell。

| | 读多少 | 传输量（11 层，int8）| @ 6.03 GB/s |
|---|---|---:|---:|
| Flash-Next 稀疏 | 每层选 2048 cell | 27 MB/token | 4.59 ms/token |
| **q36 稠密** | **每层全部 cell** | **2860 MB/token** | **497 ms/token** |

现在 decode 是 16.9 ms/token（tg64 基线 59.1 tok/s）⇒ **31 倍**。
（这组基线是 **非 peer、fp32 KV** 的；打开 peer 路径 + `--kv int8` 之后是 **61.4 tok/s（约 16.3 ms）**——
引用时必须带配置，否则两个数会打架。）
滑窗救不了：稠密 attention 必须读全部 cell，窗口外的那部分照样要搬。

核实（workflow 四读者，file:line 见代码）：
- KV 布局 `[kvh][ctx][HD]`（`q36_engine.cu:586`）
- decode 读 `[0, npos)` 全部，chunk 网格 `ceil(ctx/256)`（`q36_engine.cu:565-572`、`3512-3513`）
- prompt 的 `k_kv_f16` 把 `[0, P)` 全部 decompact 成 fp16（`q36_engine.cu:3470`）
- 每 session 每层一个池（`alloc_session`，`q36_engine.cu:2586`）
- **q36 里没有 QSA 选择**：`qsa_select.cu` / `qsa_decode_attn.cu` 是 Flash-Next 的，不在 q36 路径上。

## VMM 也不可用（MEASURED 2026-10-26，`.run/vmmtest-20261026.cu`）

CUDA 虚拟内存管理（`cuMemCreate` / `cuMemMap`）能在 host 内存和显存之间做页表映射，不走 PCIe 拷贝。
P100 上两条路都堵死：

```
CUDA devices: 4
VMM supported: 1 (rc 0)
host granularity: 2097152 bytes (2.0 MiB)
cuMemCreate 4 GiB failed: 1 (invalid argument)      # HOST 位置 + PINNED/MAX 类型
```

DEVICE 位置的分配更直接：`cuMemCreate 4 GiB: ok`、`cuMemAddressReserve 4 GiB: 0`，
但 **`cuMemMap 1 GiB: 801 (operation not supported)`** ⇒ 映射不被支持。

⇒ **KV 放主机内存（无论是拷贝还是 VMM）在 q36 上都不成立。**

## 剩下的路

1. **把 q36 的 attention 改成稀疏（QSA）**——那才是 Flash-Next 的原生路径，`qsa_select.cu` +
   `qsa_decode_attn.cu` + `kv_stream.cu` 都在树里。工作量大但是正路。
2. **KV 更小的格式**：q4_0（Flash-Next 有，q36 明确拒绝：`q36_engine.cu:7341`）。
3. **staging 缩小**（新发现，见下）。
4. **分段 KV**：上下文分段，每段独立。

（Flash-Next 另有 `qsa_kv_elastic`（`src/core/layer.cpp:680`），用 VMM 让 KV 池按需增长/收缩——
但它也依赖 VMM，同样堵死。）

## 新发现：staging 按整层分配，peer 路径下大部分是洞（MEASURED 2026-10-26）

262144 ctx 装不下的直接原因**不是 KV**：

```
strata-q36: context 262144 cells ... 0.81 GiB of VRAM free
strata-q36: not enough VRAM left for the hybrid experts' buffers and slots
  (1256 MiB needed, 832 MiB free after the weights, the context and the sessions)
```

1256 MiB = staging 1126（`2 * (max_layer + kMmqTail)`，两份整层专家）+ 130（CPU 池输出）。
**`--expert-vram` 改不了它**（staging 是固定的），四档都报同一个 1256。

而 peer 路径下，helper 持有的专家在 `stream_kick` 里被 `owned` 掩码跳过（`q36_engine.cu:4170-4173`），
**它们的字节在 staging 里从不写**。staging 957 MiB 里只有主卡 slot 那一段有用
（38 slot ⇒ 142 MiB，**815 MiB 是洞**）。

⇒ 缩 staging 能过启动，但**主卡只剩 7 slot/层**（free 832 − staging 142 − other 130 = 560 MiB），
比现在的 38 少 5 倍 ⇒ 主卡几乎退出，decode 变慢。

⇒ **staging 缩小 + q4_0 KV 一起做才保得住速度**（KV 省 1290 MiB ⇒ free 2122 ⇒ 24 slot/层）。
要保住 38 slot/层还要更多。

## 三条路的代价（workflow 核实，2026-10-26）

### A. staging 缩小（只对 peer 路径有效）

- **读集**：主卡只读 `peer_owner[li][x] == 0` 的专家的 `stage[b] + x*stride`（MMQ 按**专家 id** 寻址，
  `z = blockIdx.z` 是专家 id，不是排序位——`mmq.cuh:1004`；helper 持有的 x 在 staging 里是洞，
  但那些 tile 的 `bounds` 区间为空，不读）。
- **地板不是 slot 数**：`slot_of[x] < 0` 且非 helper 持有的专家**仍然从 staging 读**
  （`q36_engine.cu:4186-4187`）。真正的地板是「非 helper 持有的专家数」。
- **要新增一张「专家 id → 紧凑偏移」表**，串过三个读取者：`MMQ::Product`、fused `Batch`
  （`fb.blob[e] = wbase + e*L.stride`，`q36_engine.cu:3766`）、`dn.w`。
  现在的约定是「专家 id → `x*stride`」，洞之所以可接受是因为**永远不被读**，不是因为便宜。
- **收益约 300 MiB**（洞是 218/256，不是全部 256 —— slot 那 38 个是要用的）。
- **默认路径必须保持整层**：`owned == nullptr` 时是整层 H2D（`q36_engine.cu:4166`），
  且 `ident` 表假设 `x*stride`。紧凑布局只在 `STRATA_Q36_PREFILL_PEERS=1` 时成立。

### B. q4_0 KV（不是一个格式开关）

- **必须带 Hadamard 旋转**（`fwht256`，`kv_q4.cu:25-69`）：4 bit 没有旋转就不可用
  （离群通道打爆 block max，码全塌）。旋转要落在 q36 的**稠密**读路径里：
  K/V 写入前、q 打分前、输出后反旋转（镜像 `layer.cpp:1221/1263/1292`）。
- 另需：`k_attn_prep` 的量化分支、`k_attn_part` + `k_kv_f16` 的反量化分支、
  `kv4` 分派扩展、CLI。
- **约 160–240 行**。
- **精度代价（Flash-Next 上实测）**：perplexity **+8% @1K、+12% @8K**；
  `docs/DETAILS.md:88-90` 明确说 8-bit 保持默认。q36 上无任何 q4_0 实测。
- 省 1.29 GiB（int8 → q4_0，11 层）。

### C. 稀疏 attention（把 q36 改成 QSA）

Flash-Next 的原生路径（`qsa_select.cu` + `qsa_decode_attn.cu` + `kv_stream.cu` 都在树里）。
KV 可以全在 host 内存（稀疏选择只拉选中的 block）——**但 Flash-Next 的 host 副本是
QSA 的稀疏选择专用，q36 稠密读全部 cell 时传输量是 2860 MB/token（497 ms）**。
⇒ 必须先有稀疏 selection，才有流式。

## 用户提出：**KV 放 3 个 helper**（2026-10-26）

这是第三条路，绕开「主卡读全部 KV」的死结：**attention 也搬到 helper**，
helper 读自己的 KV（本地显存带宽），主卡只送 Q 上去、收 attention 输出回来。

  **这个空闲是 `auto` 装到「再放一个专家就不到 512 MiB 空闲」为止剩下的。**
- 每专家实际占 **2.012 MiB**（5876 / 2920，不是裸的 1.87 —— 那是没算对齐的）。
- KV 每层 264 MiB（int8，2 KV heads，head_dim 256，262144 cell）。

### 代价

- **helper 少装的专家要有人接**：主卡多装的 1443 个不够接，全部专家 10240 = helper 9287 + 主卡 2960 = 12247，
  ⇒ **还要 2000 个专家落回 host 内存 / CPU 池**（现在 0 个在 CPU 池）。
  这是这个方案的真代价：decode 的 entry 会有一部分落到 CPU 池。
- helper 算 attention 的时间：读自己的 KV 264 MiB/层 @ P104 ~320 GB/s = 0.87 ms/层，4 层 = 3.46 ms。
- **要新写一套 helper 上的 attention**（`RemoteExperts::begin/finish` 是给专家 GEMM 设计的，不是 attention）。

## 根因：q36 的 decode attention 把同一份 KV 读了 **8 次**（MEASURED 的推断 + 代码核实）

`k_attn_part` 的 grid 是 **`(nc, nt*H)`** —— y 维是 **query head** 数（`q36_engine.cu:3537`）。
GQA 的 8 个 query head 共享一个 KV head，于是**同一个 KV head 的 64 KB 被 8 个 block 各读一遍**。

| | grid 的 y 维 | 同一份 KV 读几次 |
|---|---|---:|
| **q36 `k_attn_part`** | `nt*H`（query head）| **8** |
| **Flash-Next `attn_chunk_kernel`** | `n_head_kv`（KV head）| **1** |

流量账（ctx 262144，int8，11 层，16 query head / 2 KV head）：

| | 每次 decode |
|---|---:|
| KV 本身 | 2.84 GiB |
| **实际读流量（×8）** | **22.5 GB** |
| @ 主卡 410 GB/s | 55 ms/token（**实测外推 108 ms**——见下面的成本模型）|

Flash-Next 的正解（`src/kernels/cuda/qsa_decode_attn.cu`）：**grid 是 `(n_chunks, n_head_kv, n_q)`**
（`:959`、`:1105`、`:1147`）—— 一个 block 一个 **KV head**，block 里的
`__shared__ float sq[G][HD]` 装着**这个 KV head 的全部 G 个 query head 的 q**，
于是 **K/V cell 在一个 block 内只读一次**（`load8`），被 G 个 query head 复用。
**这个 kernel 就在树里。**

（核实 2026-10-26：那句注释 "cuts the traffic that bounds this phase by NC"（`:590`）说的是
**q slice 从 shared memory 读的次数**——一个 lane 的 q 读一次、NC 个 cell 复用——
**不是 K/V 的读**。K/V 读一次是 grid 的结构本身带来的，不是那句注释。）

## 转向：从「KV 放 helper」到「修 attention 的 8 倍冗余」

**为什么 KV 放 helper 不是解**：helper 上同样要读 8 次（同样的 kernel 逻辑），带宽还低 20%
（P104 ~320 vs P100 410 GB/s）⇒ 22.5 GB 在 helper 上是 70 ms，比主卡更慢。
**搬家治不了流量。**

**为什么修冗余才是解**：
- 流量直接降 8 倍：22.5 GB → 2.84 GB，ctx 262144 时 attention 从 78 ms 到 ~10 ms
- **KV 留在主卡** ⇒ 不用解决「262144 装不下」的问题（那是 KV 占 2.84 GiB 的另一件事）
- 不用碰 helper 的接口（`RemoteExperts::begin/finish` 是给专家 GEMM 设计的）

**改动量（比移植 Flash-Next 的 kernel 小得多）**：q36 自己的 `k_attn_part` 是「一线程一 cell」，
把 grid 的 y 维从 `nt*H` 改成 `nt*HKV`，block 内让 8 个 query head 共享 K/V 的读：
1. grid 的 y 维：`nt*H` → `nt*HKV`（`q36_engine.cu:3537`）
2. kernel 内：分数从 1 个 head 变 8 个（K 读一次，8 份 q 各自点积）
3. V 那段同样共享（`wv[]` 变 8 份 acc）
4. **`pacc` / `pm` / `pl` 的布局不变**（`row = lt*H + h`，`lt` 是**局部** token）
   ⇒ **`k_attn_merge` 一行都不用改**（它读的本来就是局部 row）

⇒ 几十行，不是重写。

**不需要 Flash-Next 的 `reduce12` / `head_of_lane`**：那套是硬编码 12 个 head 的
（`part[16]`，lane bit1-4 ⇒ head 0-11），q36 是 G=8。
**但保留 q36 自己的「一线程一 cell」结构，这个跨 lane 的 head 归约根本不用碰** ——
每个线程算自己 cell 的 8 个 head，不做跨 lane 归约。
（这一点计划里早先写反了：不是"要一份 G=8 的变体"，是**完全不需要**。）

⇒ **ctx 262144 时 attention ≈ 108 ms/token**（decode 现在 16.9 ms/token，tg64 基线 59.1 tok/s；
这组基线是**非 peer、fp32 KV** 的，peer + `--kv int8` 是 61.4 tok/s / 约 16.3 ms）——
**decode 会被 attention 主导 6.4 倍**。

### GQA kernel 的实测斜率：**3.0 倍，不是 8 倍**（MEASURED 2026-10-26）

`STRATA_Q36_MIXER_SPLIT=1`，ctx 131072，`--bench-pp 32768 --bench-tg 32`（decode 读 32768 cell）：

| | attention ms/tok | 每层 | GDN ms/tok | **merge 单独** |
|---|---:|---:|---:|---:|
| GQA=0 | **14.511** | 1.451 | 4.810 | 0.549 |
| GQA=8 | **4.787** | 0.479 | 4.811 | 0.548 |

⇒ **attention 降 3.03 倍**（14.511 → 4.787），**不是 8 倍**。
⇒ **GDN 和 merge 一模一样**（4.810 / 4.811、0.549 / 0.548）——确认只有 attention 变了。
⇒ **merge 只占 attention 的 3.8%**（0.549 / 14.511），**不是瓶颈**（早先怀疑过它）。

**为什么不是 8 倍**：新 kernel 每个线程算 8 个 head ⇒ 寄存器从 ~8 个涨到 40 个，
占用率下降；而且 block 数少了 8 倍（`nc*2` vs `nc*16`）⇒ 长上下文的并行度也下降。
**流量确实降到 1/8，但算力利用率也降了。**

**新斜率**：0.10538 → **0.0350** ms/tok per 256 cell（3.0 倍）。
外推 **ctx 262144：108.6 → 36.1 ms/token**（不是早先估的 14）。
⇒ 262144 全开时 attention 仍是 decode 的 2 倍左右 ⇒ **GQA 之后还有空间，但不是"解决"了**。

## 数字总表（MEASURED 2026-10-26）

**早先写的二次拟合（`1.29 + 0.0626*nc + 0.000303*nc²`，外推 383 ms）被第四个点推翻了**：
65536 cell 实测 27.609，二次拟合给的是 27.6——**看起来**吻合，但 262144 的差别全在二次项上
（拟合 383 vs 线性 108）。**三个点的二次拟合不能定外推，四个点才发现它是线性的。**

⇒ 增长是**线性**的，斜率 0.105 ms/tok per 256 cell。
**这个斜率正是 8 倍读的账**：8 倍读让每 cell 的有效流量 8 倍，于是斜率也 8 倍。
去掉冗余后斜率应回到 ~0.013 ms/tok per 256 cell ⇒ ctx 262144 的 attention ≈ 14 ms/token。

**「二次项的来源（推断）」那一段是错的**（已删）：8 倍读解释的是**斜率**，不是超线性。

## 实现方案（GQA 共享，q36 自己的 kernel，几十行）

保留 q36 的「一线程一 cell」结构，只改：

1. **grid 的 y 维**：`nt*H` → `nt*HKV`（`q36_engine.cu:3537`）—— 一个 block 一个 KV head
2. **kernel 内**：分数从 1 个 head 变 G=8 个（K 读一次，8 份 q 各自点积）
3. **V 那段**：8 份 acc，共享同一份 V 的读
4. **`pacc` 布局不变**（`row = t*H + h`）⇒ **`k_attn_merge` 完全不用改**

**shared 的账**（P100 96 KB/block）：

| 方案 | shared | 每 SM block | K 读次数 |
|---|---:|---:|---:|
| 现在（1 head/block）| 7 KB | 13 | 8 |
| 8 head + 8 份 `wv` | 49 KB | 1 | 1 |
| **8 head + `vscale` 共享（推荐）** | **19 KB** | **5** | **1** |

推荐方案的 shared：`qs[8][256]` 8 KB + `sc[8][256]` 8 KB + `vscale[4][256]` 2 KB + `sh` 1 KB。
`wv`（V 的权重表）不缓存 8 份，改成把 V 的 scale 一次读进 shared，8 份 acc 各自用
（scale 读 1 次而不是 8 次，流量 +0% 而不是 +25%）。

**数值**：每个 head 的分数计算完全一样（同样的 q、同样的 K、同样的 FMA 顺序）⇒ **逐位相同**。

## 已写的代码（2026-10-26）

1. **`STRATA_Q36_MIXER_SPLIT=1`**（探针，已实测）：把 mixer 的两个分支分开计时，外加 merge 单独计时。
   在 `mixer()` 里给 attention 分支和 GDN 分支各一对 event，attention 分支内部再给
   `k_attn_part` 的出口和 `k_attn_merge` 的出口各一个。
   探针每层同步一次 ⇒ **那趟的 tok/s 不可比**，只有分支时间可比。
2. **`k_attn_part_gqa<KI8, VI8, GB>`**（新 kernel）+ **`STRATA_Q36_ATTN_GQA=N`**（N = 2/4/8，默认 0 = 老 kernel）：
   - grid y 维：`nt*H` → `nt*HKV`（一个 block 一个 KV head）
   - `qs[GB][HD]` / `sc[GB][kChunkCells]` / `vsc[(HD/kKVG)*kChunkCells]`
   - 归约（max 和 sum）对 GB 个 head **同时**做：同样的树、同样的顺序，但**每级只一次 `__syncthreads`**
     （不是每 head 一次）
   - V 那段：scale 表读一次进 `vsc`，GB 份 acc 各自用（`fmaf(sc[g][k] * wr[k], vk, acc[g])`，
     与老 kernel 的 `fmaf(wr[k], vj, acc)` 数值相同）
   - **`pacc` / `pm` / `pl` 的布局不变**（`row = lt*H + h`，`lt` 是**局部** token）⇒ **`k_attn_merge` 完全不用改**
   - 运行时条件 `H == GB * HKV`（GB 必须整除一个 GQA group），否则回退老 kernel

**shared 占用**：GB=8 时 18 KB（qs 8 + sc 8 + vsc 2）⇒ P100 的 96 KB 里每 SM 5 个 block
（老的是 7 KB ⇒ 13 个 block）。

**写的时候抓到的自己的 bug（三处，都是读代码读出来的）**：
1. else 分支（老 kernel）的 V 指针写成了 `vc[li]`（应是 `vc8[li]`）——
   那会让 `--kv int8` 的默认路径读到 fp32 的 V 缓冲。已修。
2. **归约的 race**：`m[g] = sc[g][0]` 之后立刻覆写 `sc[g][j]`，中间没有 barrier
   ⇒ 别的线程可能读到 exp 值而不是 max。已修（加 `__syncthreads()`）。
3. **sum 归约的 race**：V 那段读 `sc[g][k]`（别的线程写的），所以 sum 的树不能在 V 之前跑
   ⇒ 把 sum 挪到 V 之后（V 读完再加一次 barrier）。已修。

**还有一个更隐蔽的**：`pacc` / `pm` / `pl` 的索引必须是**局部** row（老 kernel 的 `row = blockIdx.y`，
`k_attn_merge` 读同一个局部索引），我第一版写成了全局 `t*H+h` ⇒ `t0 > 0` 时错位。已修。

**这四处说明「默认路径逐字节不变」的门必须先跑**——而且这些 bug 都在**新 kernel 里**，
只有旗标开时才走到 ⇒ 光跑默认路径的门**抓不到**它们。所以 P1（旗标开 vs 旗标关）同样必需。

**验证脚本**（`.run/R-attngqa-20261026.sh`）：
- P0：新二进制旗标关 vs 已知好二进制（`strata-q36.acc`）⇒ gen 逐字节相同
- P1：新二进制旗标开 vs P0 ⇒ gen 逐字节相同
- P2：GB = 0/2/4/8 的速度（ctx 32768，灌满）

## MiniCPM-V-4.7-35B-A3B **不是稀疏 attention**（MEASURED 2026-10-26）

用户问 `openbmb/MiniCPM-V-4.7-35B-A3B-gguf` 是不是稀疏 attention。查它的 `config.json`
（`hf-mirror.com` 能通，huggingface.co 从 box 上不通）：

| | MiniCPM-V 4.7 | q36 |
|---|---:|---:|
| 层数 | 40 | 40 |
| num_attention_heads | **16** | 16 |
| num_key_value_heads | **2** | 2 |
| head_dim | **256** | 256 |
| full_attention_interval | **4** | 4 |
| num_experts / per_tok | 256 / 8 | 256 / 8 |
| moe_intermediate_size | 512 | 512 |
| max_position_embeddings | **262144** | 262144 |
| MTP 层 | 1 | 1 |

`layer_types` 是 `linear_attention` ×3 然后 `full_attention`（40 项）——
**和 q36 的 `layer % 4 == 3` 是同一个设计**（30 层线性 attention + 10 层全 attention）。

**没有任何 sparse / DSA / top-k / indexer 的键**（`sparse_attn`、`attn_topk`、`indexer_*` 全部不存在）。

⇒ **两件事**：
1. q36 的稠密全 attention 层是**这类模型的标准设计**，不是漏做的优化
   （MiniCPM 用同样的几何、同样的 interval 4、同样的 262144 上限）。
2. **GQA 共享（不是稀疏 attention）才是那条路上正确的杠杆**——MiniCPM 也用同样的 16/2/256 几何。

（MiniCPM 的 `partial_rotary_factor = 0.25` 和 `attn_output_gate = True` q36 也有。）

## GQA 共享 kernel 的速度（MEASURED 2026-10-26）

配置：`bin/strata-q36.gqa`，`--max-context 40960 --bench-pp 32768 --bench-tg 64 --kv int8`，
三个 helper `auto`（**没有开 peer 路径**，所以 prompt 那一栏不可比，decode 可比）。
P100 主卡，**CUDA ordinal 0**。

| 档 | bench 0 | bench 1 | bench 2 | 说明 |
|---|---:|---:|---:|---|
| GQA=0 | 17.5 | 17.9 | 17.9 | 老 kernel |
| GQA=2 | 17.4 | 17.6 | 17.6 | **回退老 kernel**（16 ≠ 2×2）|
| GQA=4 | 17.5 | 17.6 | 17.6 | **回退老 kernel**（16 ≠ 4×2）|
| **GQA=8** | **21.3** | **21.2** | **21.2** | **新 kernel，+19%** |

⇒ **+19%**（17.7 → 21.2 tok/s，中间值）。
⇒ **GB=2 和 GB=4 是死代码**：launch 的条件是 `H == gb * HKV`（16 == gb×2 ⇒ 只有 gb=8 成立）。
**GB=8 就是这个模型的唯一正确值**（H/HKV = 16/2 = 8）。

**pp32768 三档都是 447–450 tok/s** ⇒ **prompt 不受影响**（prompt 走 GEMM 路径，不走 split-K）。

### 短上下文（ctx 2048）：没有被拖累（MEASURED 2026-10-26）

`--max-context 2048 --bench-pp 1536 --bench-tg 64 --kv int8`：

| | bench 0 | bench 1 | bench 2 | 中间值 |
|---|---:|---:|---:|---:|
| GQA=0 | 21.8 | 22.2 | 23.0 | 22.2 |
| GQA=8 | 21.6 | 22.1 | 22.7 | 22.1 |

⇒ **-0.5%**（噪声内）。
**为什么短上下文不亏**：ctx 2048 时 `nc = 8`，老 kernel 的 block 数是 `8 × 16 = 128`，
**已经够填 P100 的 56 个 SM** ⇒ 共享后 block 数降到 16，但那时已经不缺 block 了。
真正缺 block 的是 `nc` 很小的场合（ctx < 1024），而那个场合 attention 本身可忽略。

⇒ **GQA 共享是纯赚**：长上下文 **+19%**，短上下文 **-0.5%（噪声内）**，数值**逐位不变**。

### 真实部署配置（peer 路径）：**+50%**（MEASURED 2026-10-26）

`--max-context 40960 --bench-pp 32768 --bench-tg 64 --kv int8`，三个 helper `auto`，
**peer 路径全开**：`REMOTE_ZEROCOPY=0 HELPER_ASYNC=1 HELPER_PARALLEL=1 Q8_SM60=1
HELPER_PARALLEL_MARSHAL=1 FIXED_SLOTS=1 PREFILL_PEERS=1 PREFILL_PEERS_HOST=1 PEER_SUM=1
PEER_I8=1 PF_F16_CUDA=1 DENSE_F16_ACC=1`

| 档 | bench 0 | bench 1 | bench 2 | 中间值 |
|---|---:|---:|---:|---:|
| GQA=0 | 33.8 | 34.2 | 34.2 | 34.2 |
| **GQA=8** | 50.4 | 51.3 | 51.4 | **51.3** |

⇒ **+50%**（34.2 → 51.3 tok/s）。
pp32768 两档都是 605–607 tok/s ⇒ **prompt 不受影响**。

**为什么比没开 peer 时的 +19% 大**：peer 路径把主卡的专家活分给 helper，主卡空出来 ⇒
同样的 tok/s 下 **attention 在主卡上的占比更高** ⇒ 去掉 8 倍冗余的收益更大。

### ⚠️ 短上下文 **反而慢 2.6%**（MEASURED 2026-10-26）——不是纯赚

`--max-context 2048 --bench-pp 512 --bench-tg 64 --kv int8`，peer 路径全开
（**和 59.1 基线同条件**）：

| 档 | bench 0 | bench 1 | bench 2 |
|---|---:|---:|---:|
| GQA=0 | 60.5 | 61.1 | **61.1** |
| GQA=8 | 58.5 | 59.4 | **59.5** |

⇒ **-2.6%**（61.1 → 59.5）。

**为什么**：ctx 2048 时 attention 只占 1.81 ms/tok（decode 总共 16.4 ms ⇒ 11%），
**去掉 8 倍读只省约 1.2 ms**；而新 kernel 的代价更大：
- **block 数从 `nc*16 = 128` 降到 `nc*2 = 16`** —— P100 只有 56 个 SM，16 个 block **填不满**
- **寄存器压力**：`a[8] + s[8] + acc[8] + m[8] + l[8] = 40` 个寄存器/线程 ⇒ 占用率下降

⇒ **两个方向相反的效应，短上下文时代价赢。**

**必须找交叉点**——在交叉点以下用老 kernel，以上用新 kernel。

### ❗ 第一次找交叉点**测法错了**，得出了反结论（MEASURED 2026-10-26）

`R-gqacross-20261026` 用 `--bench-pp 512 --bench-tg 64` 扫 ctx 2048/4096/8192/16384：

| ctx | GQA=0 | GQA=8 | Δ |
|---:|---:|---:|---:|
| 2048 | 61.1 | 59.5 | **-2.6%** |
| 4096 | 61.0 | 59.5 | **-2.5%** |
| 8192 | 61.5 | 59.3 | **-3.6%** |
| 16384 | 61.1 | 59.1 | **-3.3%** |

**四个档全负，而且不随 ctx 变化** ⇒ **这不是 attention 的成本，是 kernel 的固定代价**。

**为什么**：`--bench-tg 64` 只生成 **64 个 token**，prompt 只有 512 ⇒
**decode 最多读到 512+64 = 576 个 cell**（`nc = 3`）。
**`--max-context` 只是分配的大小，不是 decode 实际读的长度。**
⇒ 这四个档里 **attention 几乎不存在**，测的全是新 kernel 的固定代价
（40 个寄存器/线程的占用率损失 + block 数从 `nc*16` 降到 `nc*2`）。

**教训**：**测 attention 的收益，必须让 decode 本身读长上下文** ——
`--max-context` 变大不等于 decode 读得长，要 `--bench-pp`（prompt 把上下文填上）才算。
（`R-gqaspeed` 和 `R-gqapeer` 用的是 `--bench-pp 32768`，所以那两档是**对的**。）

⇒ 真正的两个端点（都是 `--bench-pp 32768`，decode 读 32768 cell）：
- **decode 读 576 cell**（`--bench-pp 512 --bench-tg 64`）：**-3%**
- **decode 读 32768 cell**（`--bench-pp 32768 --bench-tg 64`，peer）：**+50%**

中间用 `R-gqacross2-20261026`（`--bench-pp 4096/8192`）补。

### 交叉点：**decode 读 ~2000–4000 cell**（MEASURED 2026-10-26）

`--bench-pp P --bench-tg 64`，peer 路径全开，ctx = P+1024：

| decode 读的 cell | GQA=0 | GQA=8 | Δ | 档 |
|---:|---:|---:|---:|---|
| ~576 | 61.1 | 59.5 | **-2.6%** | `--bench-pp 512` |
| ~4160 | 58.2 | **59.4** | **+2.1%** | `--bench-pp 4096` |
| ~8256 | 54.3 | **58.4** | **+7.6%** | `--bench-pp 8192`（三趟 57.1/58.4/58.4）|
| ~32832 | 34.2 | **51.3** | **+50%** | `--bench-pp 32768` |

⇒ **交叉点在 decode 读 2000–4000 cell（ctx 约 4K）**。

**为什么短上下文会亏**：decode 读 576 cell 时 attention 只占 1.81 ms/tok 的 **11%**，
去掉 8 倍读只省 ~1.2 ms；而新 kernel 的**固定代价**是
`a[8]+s[8]+acc[8]+m[8]+l[8] = 40` 个寄存器/线程（占用率降）+ block 数从 `nc*16` 降到 `nc*2`。

⇒ **实用规则**：`ctx >= 4096` 开 GQA，以下不开（或者按 `attn_gqa()` 里加一行自动判断）。

### 自动开关（`STRATA_Q36_ATTN_GQA=auto`）

`attn_gqa()` 现在返回：
- **不设 / 0** ⇒ **老 kernel**（默认，逐字节不变——这是出货的默认）
- **2 / 4 / 8** ⇒ 强制共享形状
- **`auto`（或任何负数）** ⇒ **按这次调用实际要读的 cell 数决定**：
  `nc * 256 >= 2048` 就用共享形状，否则用老 kernel

**判据用的是 launch 即将用的那个 `nc`**，不是分配的 `--max-context`：
长上下文的最后一个 chunk 和短 prompt 都能算对。

**阈值 2048 的来由**：实测 576 cell 时共享形状慢 2.6%，4160 cell 时快 2.1%
⇒ 交叉点在两者之间；2048 偏保守（错了只亏 ~1%，而不是 3%）。
**旗标默认仍是关**，所以默认路径逐字节不变（自动是 opt-in 的一个取值）。

**为什么长上下文赚得多**：attention 是**线性**增长的（0.105 → 0.035 ms/tok per 256 cell），
而 decode 的其余部分（专家 GEMM）是常数 ⇒ 上下文越长，attention 占比越高，共享的收益越大。
