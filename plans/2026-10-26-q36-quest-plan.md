# Quest on q36: the plan (2026-10-26)

## 目标

decode 的 attention 只读 top-k 个 256-cell chunk，而不是全部。GQA 之后 262144 仍有 ~36 ms/token，
Quest 要把它压到十几 ms。

## 和 GQA 的根本差别（必须说清）

- **GQA 共享：逐位不变**（同样的 q、同样的码、同样的 FMA 顺序）⇒ 只换流量。
- **Quest：是近似**（softmax 只在一部分 cell 上做）⇒ **数值会变**，必须测精度代价。
  ⇒ 必须是 opt-in，且要有一份「和稠密路径的 token 一致率」实测。

## 设计（沿用 q36 已有的 256-cell chunk 作为 Quest 的 page）

1. **元数据**：每个 chunk、每个 KV head 存 K 的 per-dim min/max（int8，复用现有 scale）：
   `kmin[chunk][kvh][HD]`、`kmax[chunk][kvh][HD]`。262144 时 = 1024 chunk × 2 × 256 × 2 B = **1 MB**。
   在 `k_attn_prep` 写 K 之后算（chunk 内 256 个 cell 的分组 min/max）。
2. **选择 kernel**（每 row 一次，每层一次）：
   `score[chunk] = Σ_i max(q[i]*kmin[i], q[i]*kmax[i])`（Quest 的上界估计）
   ⇒ top-k 个 chunk ⇒ 写一张 `sel[row * n_chunk + chunk]` 的 uint8 掩码（262144 时 1 KB）。
3. **k_attn_part**：block 入口 `if (!sel[row][c]) return;` —— **在任何 K/V 读之前**返回。
4. **k_attn_merge**：跳过 `sel == 0` 的 chunk（它已经只按 nc 循环，读一个字节即可）。

⇒ **改动最小**：不改 grid、不改 pacc 布局、不改 launch 结构。

## 代价

- 选择 pass：每 row 每层 1024 chunk × 256 MAC = 262K MAC ⇒ 11 层 = 2.9M MAC ⇒ **可忽略**。
- 精度：**未知，必须测**。MInference 报「20% index-building overhead」（那是 prefill 的）。
  q36 上要自己量。

## 门的顺序

1. 旗标关 ⇒ **逐字节不变**（默认路径不动）
2. 旗标开、k = nc（全选）⇒ **逐字节等于稠密**（证明选择/掩码逻辑本身没有 bug）
3. 旗标开、k = 真值 ⇒ 测 token 一致率 + 速度
4. 找 k 的曲线（k = 128/256/512/1024）

## 已实现（2026-10-26）

| 部件 | 位置 | 说明 |
|---|---|---|
| `Sess::qkmin / qkmax` | `q36_engine.cu` 的 `struct Sess` | 每 session 每层一对 int8 buffer |
| 分配 | `alloc_session` | `n_kv_heads × ceil(ctx/256) × head_dim` 字节；262144 时 ≈ 1 MB |
| 串联 | `load_cur` | 跟着 session 切换 |
| `k_quest_bounds` | 新 kernel | chunk 写完后扫一遍码，算 per-(chunk, kv head, dim) 的 min/max |
| `k_quest_sel` | 新 kernel | 每 row 一个 block：`Σ max(q·lo, q·hi)·smax` 的界，取 top-k |
| `k_attn_part` / `k_attn_part_gqa` | 加了 `sel` 参数 | **在 K/V 读之前** `if (sel && !sel[row][c]) return;` |
| `k_attn_merge` | 加了 `sel` 参数 | 跳过没选的 chunk |

**旗标**：`STRATA_Q36_QUEST=K`（K = 每 row 保留多少 chunk，0/不设 = 关 = 老路径逐字节不变）。

**Q0/Q1 两个门已过**（MEASURED 2026-10-26）：

| 门 | 结果 |
|---|---|
| Q0 旗标不设 vs 已知好二进制 | **gen 逐字节相同** ✓ |
| Q1 `QUEST=1024`（>全部 chunk，等于全保留）vs Q0 | **gen 逐字节相同** ✓ |

⇒ **Q1 证明选择/掩码/merge 跳过这套管道本身没有 bug**：全保留时结果等于稠密。

### 精度实测（MEASURED 2026-10-26，`R-questacc3` / `R-gate2`）

**测法**：10 条真 parity prompt 循环 560 次 = **16184 cell**（64 个 chunk），
`--max-context 32768`，每档生成 32 个 token 比对 `gen:`。

| 档 | 保留比例 | 32 个 token | 判定 |
|---|---:|---|---|
| k=0（稠密）| 100% | 基准 | — |
| k=4 | 6% | **第 30 个 token 分叉**（`760 9662 1204` vs `248045 846 198`）| **测试有鉴别力 ✓** |
| k=8 | 12% | **逐字节相同** | ✓ |
| k=32 | 50% | **逐字节相同** | ✓ |
| k=128 | 100%（>64 chunk，等于全保留）| **逐字节相同** | ✓（同时复核了 Q1 门）|

⇒ **k=8 起，32 个 token 与稠密逐字节相同** — 但这是 **64 个 chunk 里留 8 个（12%）**。
⇒ **k=4 会分叉** ⇒ 这个精度测试**能失败** ⇒ k=8/k=32 的"逐字节相同"是真的，不是测不出来。
（这是必须有的对照：早先两版测法（9000 个重复 token、578 cell 的 prompt）**没有鉴别力**，
三档全都"逐字节相同"是因为根本没触发选择。）

**k 不能跨 prompt 长度直接比**：速度曲线是 decode 读 ~32832 cell（129 chunk，`--bench-pp 32768`）。
同一个保留比例：k=8 @ 129 chunk ≈ **6%** = 这里分叉的 k=4；k=16 @ 129 chunk ≈ **12%** = 这里逐字节相同的 k=8。
⇒ 32k 上「k=8 又快又准」还没被这条测法证明。

### ⚠️ 32k 的第一版测法**无效**（MEASURED 2026-10-26，`R-questacc5`）

三个障碍叠在一起，第三个才致命：

1. **32779 个 id 塞不进命令行**：一条 argv 上限 128 KB（`MAX_ARG_STRLEN`），32779 个 id = **159 KB**
   ⇒ `env: 参数列表过长`（rc=126，三档全挂）。
2. **改走 `--serve`**（从 stdin 读 `GEN` 行，159 KB 没有上限）：能跑，prompt 32779 cell 全部读进去
   （pp32768 读 32779，用了 53.9 s，609 tok/s）。
3. **`--serve` 遇 EOS 就停** ⇒ 答案只有 **21 个 token**（`248046` 是 EOS），
   而 16k 的分叉在**第 30 个 token** ⇒ **这条测法根本看不到分叉**。

⇒ **k=0/4/8/16 四档的 21 个 token 全都逐字节相同**（`R-questacc5`）——
**这不是"32k 上 k=4 也准"，是"这条测法只有 21 个 token"**。
（`--tokens` 路径按 `--n` 走、**不看 EOS**，16k 那次就是它测的 32 个 token。）

⇒ 修法：**给引擎加 `--tokens-file`**（`q36ref.cu` 和 `src/program/generate.cpp` 早就有，这个引擎没有），
id 从文件读，`--n 32` 出满 32 个 token。`R-questacc6` 跑 k=0/4/8/16。
**k=4 是那道有鉴别力的对照**：16k 上它分叉，这里必须也分叉，否则整条测法作废。

### 32k 的精度（MEASURED 2026-10-26，`R-questacc6` / `R-questacc7`）

**测法**：1134 次 parity prompt 循环 = **32779 cell**（129 chunk），`--max-context 40960`，
`--tokens-file` + `--n 32`（**越过 EOS**，出满 32 个 token）。GQA 关。

| 档 | 保留比例 | 32 个 token | 96 个 token |
|---|---:|---|---|
| k=0（稠密）| 100% | 基准 | 基准 |
| **k=4** | **3%** | **逐字节相同** | **逐字节相同**（96 个）|
| k=8 | 6% | **逐字节相同** | **逐字节相同**（96 个）|
| k=16 | 12% | **逐字节相同** | — |

⇒ **32k 上 k=4（只留 129 个 chunk 里的 4 个）连着 96 个 token 都与稠密逐字节相同。**

**但 k=4 这条测法在 32k 上没有分叉，而 16k 上它分叉** ⇒ 两种解释，**这条数据分不开**：
(a) 上下文更长时同样的 k 更准（重要信息的分布变了）；
(b) 32k 上它的分叉点比第 96 个 token 更靠后。
**不把它当成"k=4 在任何长度都准"。** 16k 那道分叉（k=4，第 30 个 token）仍然是真的。

⇒ **能下的结论只有一条**：**在 32k 的 decode 上，k=8（6% 保留）不改变任何一个 token**，
而它在 GQA 关时是**最快的档（42.1 tok/s，+23%）**。
⇒ **「k=8 又快又准」在 32k 上成立**（两个数都在 32k 上量的）。
k=4 虽然也准，但 3% 保留在 16k 上会分叉 ⇒ **出货只用 k=8，不碰 k=4**。

## 实测结果（MEASURED 2026-10-26）：**当前实现是负收益**

`--bench-pp 32768 --bench-tg 64 --kv int8`，peer 路径全开，ctx 40960（**GQA 关**，所以 k=0 是稠密基线 34.5）：

| k | tg64 tok/s | 相对 k=0 |
|---:|---:|---:|
| 0（关）| **34.5** | — |
| 1024（≈全保留）| 12.0 | **-65%** |
| 256 | 11.9 | **-66%** |
| 64 | 14.1 | **-59%** |

**pp32768 四档都是 606 tok/s** ⇒ prompt 不受影响（走 GEMM 路径）。

⇒ **选择 pass 的成本远超省下的读。** 而且 **k=1024 和 k=256 几乎一样慢**，
说明慢的是**选择本身**，不是 attention 读了多少。

### 根因（读代码确认）

`k_quest_sel` 每 (row, chunk) 做：
1. **`smax` 每维重复扫**：`for (k = 0; k < n; ++k) ksp[k * nsg + d/kKVG]`——
   256 个线程**各自扫一遍 256 个 cell** ⇒ 每 chunk **65536 次 scale 读**（本可以是 1024 次）
2. **一次完整 256 级树归约**，`nc = 128` chunk ⇒ **128 次串行归约 + 256 次 `__syncthreads`**，每层每 row

⇒ 每层每 row ≈ 128 × (65536 读 + 树归约) ≫ attention 实际读的量。

### 修了两轮，才把 k=32 拉到正收益

| 版本 | 选择 pass 的做法 | k=128 | k=32 |
|---|---|---:|---:|
| v1 | 每 chunk 一次 256 级树归约 + 每线程扫全部 scale | 12.0 | 14.1 |
| v2 | warp 归约，`smax` 交给 **lane 0 串行扫** | **6.5**（更差）| — |
| **v3** | warp 归约 + **warp 并行扫 `smax`**（32 lane）| 21.1 | **35.9** |

**v2 是反优化**：把 `smax` 交给 `lane 0` 扫 1024 个 scale ⇒ 串行，比原来的并行扫慢 32 倍。
**教训：并行度不能被"减少重复计算"换掉。**

**v3 后的完整表**（`--bench-pp 32768 --bench-tg 64`，ctx 40960，GQA 关）：**k=32 转正，k=128 仍负**：

| k | tg64 | 相对 k=0 |
|---:|---:|---:|
| 0（稠密）| 34.4 | — |
| 128（160 chunk 的 80%）| 21.1 | **-39%** |
| **32（160 chunk 的 20%）**| **35.9** | **+4.4%** |

**为什么 k=128 还亏**：`k_attn_part` 的 grid 是 `(nc, nt*H)`，**block 数固定**，跳过的 block 只是早返回
⇒ **kernel 的调度成本不变**，省的是显存带宽。k=128 省 20% 带宽盖不住选择 pass 的固定成本；
k=32 省 80% 才盖过。

⇒ **选择 pass 的固定成本 ≈ 10 ms/token**（从这个差算出来的）。要让它有意义得压到 <1 ms。

### k 再往下（MEASURED 2026-10-26，`R-questk3`，GQA 关）

同一二进制，`--bench-pp 32768 --bench-tg 64`，ctx 40960，peer 路径全开。k=32 **复现 35.9**。

| k | 保留（~129 chunk）| pp32768 | tg64 | 相对 34.3 |
|---:|---:|---:|---:|---:|
| 0 | 100% | 606.4 | 34.3 | — |
| **8** | **6%** | 606.4 | **42.1** | **+23%** |
| 16 | 12% | 606.1 | 40.2 | +17% |
| 32 | 25% | 606.0 | 35.9 | +4.7% |

⇒ **峰值在 k=8**，不是 k=32。k 再小，省下的带宽仍然大于选择 pass 的固定成本。
⇒ **pp32768 四档都是 606** ⇒ prompt 仍走 GEMM，不受选择影响。
⇒ **这个 +23% 还不能当成准确度免费**：6% 保留在 16k prompt 上就是分叉的那档（k=4 / 64 chunk）。
同一保留比例在 32k 上要重测（`R-questacc5`，32779 cell，k=0/8/16）。

### GQA 叠 Quest：**负收益**（MEASURED 2026-10-26，`R-questk3` 第二段）

同一条件，`STRATA_Q36_ATTN_GQA=auto`（这条 decode 读 32768 cell，自动规则选共享形状）：

| 档 | pp32768 | tg64 | 相对 GQA 单独 |
|---|---:|---:|---:|
| GQA，Quest 关 | 606.2 | **51.7** | — |
| GQA + k=8 | 605.8 | 41.6 | **-20%** |
| GQA + k=32 | 606.2 | 37.4 | **-28%** |

⇒ **共享已经把 8 倍读拿掉之后，选择 pass 的固定成本大于剩下的带宽。**
k=8 在 GQA 关上是峰值（42.1，+23%），叠上 GQA 反而比 GQA 单独慢 10 tok/s。
⇒ **两条路不叠加。** 长 decode 用 GQA（51.7，数值不变）；Quest 只在 GQA 关时有速度，而且那个速度还欠 32k 精度。

时间账（同一条 bench）：稠密 29.2 ms/tok，Quest k=8 23.8（净省 5.4），GQA 19.3，GQA+k=8 24.0。
GQA 之上再跑选择，净亏约 4.7 ms/tok。

### 还没做（下一步）

1. **32k 的精度**（`R-questacc6`）：`--tokens-file` + `--n 32`（越 EOS），k=0/4/8/16。
   **k=4 是有鉴别力的对照**（16k 上它第 30 个 token 分叉）。
2. **把选择 pass 的固定成本压到 <1 ms**（现在的 ≈ 10 ms/token）：
   - **`k_quest_sel` 的 grid 是 `nt*H = 16`（decode T=1），P100 有 56 个 SM ⇒ 只用了 28%**
     ⇒ grid 改成 `(nblk, nt*H)`，每 block 处理 `nc/nblk` 个 chunk ⇒ 并行度 ×nblk
   - **top-k 要两级**（每 block 出候选，再合并）
   - **`smax` 每 chunk 算一遍就够**（它只依赖 (chunk, kv head)，不依赖 row）⇒ 现在每 row 重算一次
3. ~~**GQA=auto 叠 Quest**~~ ⇒ 已测，负收益（见上）

**为什么必须先压成本**：GQA 已经把流量降了 8 倍，Quest 再降也只剩带宽的零头，
而选择 pass 的固定成本（≈ 10 ms/token）是**和上下文无关**的 ⇒ 现在它比省下的还多。
压到 <1 ms 之后，GQA 叠 Quest 才有可能是正的。

## 不做

- 不做 per-page 的 host 内存 KV 流式（Quest 的收益先在显存内拿到，流式是另一件事）
- 不改 prompt 路径（prompt 走 GEMM，不是这个 kernel）

## 结论（2026-10-26）

**Quest 在 q36 上是可行的，但只值一个 opt-in 的旗标，不是出货路径。**

| | 结论 | 依据 |
|---|---|---|
| 数值 | **k=8（6% 保留）在 32k 上 96 个 token 逐字节等于稠密** | `R-questacc6` / `R-questacc7` |
| 速度 | GQA 关时 **+23%**（42.1 vs 34.3）；**GQA 开时 -20%** | `R-questk3` |
| 原因 | GQA 已经把流量降 8 倍，Quest 再降只剩零头，而**选择 pass 的固定成本 ≈ 10 ms/token** | `R-questk3` + 代码核实 |
| 默认路径 | **旗标不设 ⇒ 逐字节不变**（parity 门 `gen: 220 16 15 15 15 20332 1740 369`）| `R-parity` / `R-parity2` |

⇒ **出货的是 GQA（`STRATA_Q36_ATTN_GQA=auto`），不是 Quest。**
Quest 留着的理由：**它是 q36 上唯一一条「训练无关的 decode 侧稀疏」的路**，
而且 **它已经证明了自己的两件事**：稀疏选择在 q36 的精度代价可控（k=8）、
以及**真正的瓶颈是选择 pass 本身，不是稀疏化**。
下一版的选择 pass（并行化 + 两级 top-k + smax 复用）若能把 10 ms 压到 <1 ms，
GQA + Quest 才有可能是正的 —— 那时它能让 ctx 262144 的 decode attention 从 36 ms/token 再降一截。

**它也是「MInference / DCA / DSA 三条路都不通」之后，剩下唯一可走的 decode 稀疏化路径**
（见 `plans/2026-10-26-q36-sparse-attention-survey.md`）。
